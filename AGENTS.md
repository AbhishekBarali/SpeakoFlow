# AGENTS.md

This file provides guidance to AI coding assistants working with code in this repository.

## Development Commands

**Prerequisites:**

- [Rust](https://rustup.rs/) (latest stable)
- [Bun](https://bun.sh/) package manager

**Core Development:**

```bash
# Install dependencies
bun install

# Run in development mode
bun run tauri dev
# If cmake error on macOS:
CMAKE_POLICY_VERSION_MINIMUM=3.5 bun run tauri dev

# Build for production
bun run tauri build

# Frontend only development
bun run dev        # Start Vite dev server
bun run build      # Build frontend (TypeScript + Vite)
bun run preview    # Preview built frontend
```

**Linting and Formatting (run before committing):**

```bash
bun run lint              # ESLint for frontend
bun run lint:fix          # ESLint with auto-fix
bun run format            # Prettier + cargo fmt
bun run format:check      # Check formatting without changes
bun run format:frontend   # Prettier only
bun run format:backend    # cargo fmt only
```

**Model Setup (Required for Development):**

```bash
mkdir -p src-tauri/resources/models
curl -o src-tauri/resources/models/silero_vad_v4.onnx https://blob.handy.computer/silero_vad_v4.onnx
```

For detailed platform-specific build setup, see [BUILD.md](BUILD.md).

## Architecture Overview

SpeakoFlow is a cross-platform desktop voice assistant (dictation, AI chat panel, screen vision, and a local-first personal memory) built with Tauri 2.x (Rust backend + React/TypeScript frontend). It started as a fork of [Handy](https://github.com/cjpais/Handy) by CJ Pais; the local dictation core (Whisper/Parakeet pipeline, VAD, overlay, settings architecture) traces back to that project. See [README.md](README.md#credits--license) for full attribution.

### Backend Structure (src-tauri/src/)

- `lib.rs` - Main entry point, Tauri setup, manager initialization
- `managers/` - Core business logic:
  - `audio.rs` - Audio recording and device management
  - `model.rs` - Model downloading and management: resilient downloads that auto-retry with exponential backoff and resume from a `.partial` file via HTTP `Range` (`attempt_download`, `AttemptOutcome`, `HttpStatusError` sorting transient vs. permanent failures), plus an ordered source list (`download_candidates`): SpeakoFlow's own mirror first (`mirror_url_for`; none published yet), then the canonical URL, then the catalog's mirrors. **The bundled catalog is Handy's v2** (`catalog/catalog.json`, 69 models, every one listed; the old list showed only the five `recommended` ones). Each model pins a Hugging Face `revision` and each file a `sha256`, so the URL is `resolve/<commit>/<file>` rather than `resolve/main`, a later push to the repo cannot change the bytes fetched, and `verify_sha256` checks every finished download whichever host served it. That hash is also why `CatalogModel::mirror_urls` offers a mirror (`blob.handy.computer`, someone else's bandwidth, so last) only for a file with a hash and a model with a pinned revision: without the hash there is nothing to check an untrusted host's file against. The list is ordered by `catalog_order` (editorial rank, then recommended, accuracy, speed, name), the same rule as the frontend's `compareCatalogOrder`. It also owns **SpeakoFlow Mini** (`SPEAKOFLOW_MINI_MODEL_ID`), our own 0.8B English dictation-cleanup fine-tune. It is a `LlamaCpp` model but not a chat model, and `is_cleanup_specialist` is what encodes that: the predicate matches a normalized model _name_, not just the catalog id, so the same weights are recognized whether they arrived as the bundled download, a `.gguf` the user imported, or a model served from their own Ollama/LM Studio endpoint. Being a specialist changes three things — the cleanup catalog features it, the assistant catalog hides it (it cannot converse), and the request path drops the app's own prompt scaffolding. The derived flag reaches the frontend through `ModelInfo.is_cleanup_specialist`, stamped in `get_available_models` / `get_model_info` rather than at the ~30 construction sites so every insert path is classified by one rule
  - `transcription.rs` - Speech-to-text processing pipeline. **Every local speech model runs on transcribe.cpp** (`transcribe-cpp` `=0.4.0`, pinned exactly because its ABI is pre-1.0), GGUF catalog models and whisper.cpp `.bin` files alike: transcribe.cpp reads the format from the file header, so `EngineType::Whisper` and `EngineType::TranscribeCpp` share one load arm and one run plan. `transcribe-rs` (whisper-rs plus its ONNX engines) is gone, and DirectML with it; a model of one of those engine types is refused at load with `retired_engine_message` before its download state is read (see `legacy_models.rs`). `ort` stays in the build only for Silero VAD (through `vad-rs`) and meeting diarization, and because pyke's prebuilt Windows ORT is compiled with the DirectML provider, `speakoflow.exe` still imports `DirectML.dll`, which Windows 10 1903+ ships and nothing bundles (build.rs NOTE). **Where speech runs is one setting pair**, `transcribe_accelerator` (`Auto` / `Cpu` / `Gpu`) and `transcribe_gpu_device`, a stable device key (`device_key`: the backend's `device_id`, the PCI bus id on Vulkan, or the name where there is none, as on Metal; the encoding upstream Handy stores), never a registry index, since transcribe.cpp's indices are process-local. `load_target` / `transcribe_cpp_load_options` map it: `Auto` leaves the device unset, so transcribe.cpp takes the first GPU that initializes, every dedicated one before any integrated one, else the CPU; a saved key that is gone logs a warning and falls back to that policy instead of failing the load; `Gpu` without a key means `Auto`. `settings::migrate_accelerator_settings` carries `whisper_accelerator` over and drops `whisper_gpu_device` and `ort_accelerator`. `cpu` and `auto` keep their meaning; `gpu` becomes `auto`, because the device it named was `whisper_gpu_device`, an index into whisper.cpp's own device list that says nothing about transcribe.cpp's, and `ort_accelerator` belonged to an engine that no longer exists. The x64 build running emulated on a Windows on ARM PC never registers a GPU backend (`transcribe_gpu_disabled_for_host`, via `IsWow64Process2` resolved at run time; Handy #1731), because the emulated Vulkan path is not reliable for ggml's compute shaders, so there every choice means the CPU and the dropdown offers only Processor. The UI is one dropdown, "Speech processing" in Settings → Advanced → Performance (`AccelerationSelector`), no longer behind Experimental features. Compute devices are listed in a short-lived model-less worker on every platform (see `engine_supervisor/` below), so a Vulkan driver that crashes while enumerating costs a GPU listing, never the app; `--probe-devices` (one JSON line) and `--list-devices` remain as script and CI audit flags, but the app no longer spawns them. On x86-64 a CPU without FMA3 lists no GPU at all, because ggml's Vulkan backend raises an uncatchable SIGILL there, and its workers are CPU-only (`gpu_allowed`), or the first load of every session crashed one. A device probe that fails without a crash is not retried on every GPU-list read (`Shared::probe_failed`) until Speech processing changes. The CPU instruction floor is transcribe-cpp-sys's job now: dynamic-backends builds (Windows x64, Linux) force `GGML_NATIVE=OFF` and pick CPU kernels at run time, every macOS build sets it off, and Windows ARM64 gets it through `TRANSCRIBE_CMAKE_ARGS`. The CI step that exported `GGML_NATIVE=OFF` and the `whisper_cpu_supported` refusal both existed for the statically linked whisper.cpp inside transcribe-rs and went with it. **A Parakeet-family model (Parakeet, Nemotron) on a GPU gets a one-thread session** (`transcribe_cpp_session_threads`): its RNN-T decoder runs on the CPU, one tiny step per frame and token, and with the default every step waits for all logical CPUs to be scheduled. Under a background build that held local dictations on "Transcribing…" for 15–17 s, while one thread measured the same as sixteen on an idle machine; raising thread priority instead made it worse. Other families and CPU-only models keep every thread. When a dictation ends and the live stream is still behind after `STREAM_FINALIZE_PATIENCE` (2 s), a native stream on a GPU drops its backlog and the recording is transcribed in one pass; elsewhere it is waited for as before. Parakeet Unified's buffered stream gets 560 ms of silence before it finalizes (`BUFFERED_STREAM_TAIL_PAD_SAMPLES`), because it decodes its last chunk with no audio after it and dropped the last word. **A stream's transcript is `StreamText::full`, never `display()`** (committed + tentative): transcribe.cpp's committed text is append-only, and a model that re-decodes everything it has heard on each feed (Moonshine Streaming) rewrites words it already committed. Finalize then leaves the stale committed text as it is and appends nothing, so `display()` pasted wrong words with the end of the dictation missing ("Are" for "Our surprising is not that bad"; upstream Handy 09aaf4d3). The overlay gets `live_split`, which keeps only the committed words `full` still agrees with, so the preview always reads as the model's current hypothesis instead of stale words plus a fragment cut mid-word. **Custom words reach the model two ways** (`transcribe_cpp_run_plan`): Whisper gets them as its initial prompt (a run extension every other family rejects), and a model with `Feature::Vocabulary` gets them as vocabulary (Handy #2284). Either sets `RunPlan::words_biased`, which skips the fuzzy `apply_custom_words` pass, since a second pass over text the model already biased can only corrupt it; only a model given neither gets the fuzzy pass
  - `engine_supervisor/` - **Every transcribe.cpp call runs in a worker process** (port of Handy #2208; issue #82): `speakoflow.exe --transcribe-worker`, recognised in `main.rs` before CLI parsing, Tauri, single-instance, portable mode or logging, none of which a worker may touch. Backend init, device listing, model load, inference and streams all run there, so a GPU driver fault, a `GGML_ASSERT` abort or a hang ends the worker instead of the app, which used to crash or sit on "Transcribing…" for good. `EngineSupervisor` (`supervisor.rs`) is the only owner; nothing else sees processes. `protocol.rs` is strict request/response, one frame per message (`[u32 json][json][u32 pcm][f32 pcm]`, JSON because transcribe-cpp's serde impls round-trip NaN through `null`), with a 1 GiB section cap so a garbage length cannot become a huge allocation; 10 minutes of PCM costs about 10 ms to send. A worker that crashes or hangs while it has GPU backends marks the GPU unavailable for the session (one warning) and the call is retried once in a CPU-only worker (`--cpu-only`, which restricts transcribe.cpp to CPU backends before any GPU code runs, so a driver that dies while initialising cannot take the fallback with it); a second failure is a plain error that ends in the pill's "Try again". Changing Speech processing or the GPU re-enables the GPU (`retry_transcribe_gpu`). Deadlines scale with the audio above a floor (30 s on a GPU, 120 s on the CPU), and a load gets `LOAD_TIMEOUT` (180 s) because a slow load is not a hung one (Handy #1841). **Cancel goes through transcribe.cpp's abort callback first** (`CANCEL_GRACE` 750 ms before the worker is stopped instead), so Esc stops a dictation without throwing the loaded model away; a cancelled dictation (`transcribe_for_dictation`) ends in "Dismissed · Undo", not a failure. A batch run waits for a live stream instead of ending it, because a meeting can transcribe beside a dictation. So does a model load or unload (a model switch, a Speech processing change, an "Immediately" unload after another transcription): stopping the worker ended the dictation's stream, and its batch fallback then found no model. Only quitting skips that wait (`EngineSupervisor::unload_now`). One worker holds a model at a time and lives exactly as long as it, so unloading returns its CPU and GPU memory to the OS; unloads from the main or a command thread never wait for it (`request_unload`), and only `delete_model` does, because Windows will not delete a file the worker still has mapped. On Windows the worker is created with `CREATE_NO_WINDOW` and put in a kill-on-close Job Object (`utils::assign_child_to_kill_on_close_job`, shared with the llama.cpp sidecar), and every worker exits when its stdin closes, so a crashed or killed app leaves none behind. Its stderr goes into the app log, so engine lines still appear in `speakoflow.log`. `lib.rs::release_before_exit` stops it (at most 2 s) because a Windows in-app update overwrites the exe it runs from. Debug builds only: `SPEAKOFLOW_TRANSCRIBE_WORKER_EXE` points tests at a built `speakoflow.exe` (under `cargo test` the current exe is the test harness), and `SPEAKOFLOW_WORKER_FAULT=<abort|segv|hang>@<init|list|load|run|feed|finalize>` (with `_ONCE` and `_GPU_ONLY`) injects a fault for the `#[ignore]`d recovery tests; none of it is compiled into release builds

  - `transcription/policy.rs` - **How audio is decoded follows the model, never the overlay style.** `live_decode` / `batch_decode` take `ModelTraits` (`streaming`, and `long_form` from `Feature::LongForm`, which is Whisper today) plus `long_form_chunking`: a streaming model always streams and takes a whole clip in one run; any other model is cut into long-form chunks unless it keeps its accuracy on long audio itself; with chunking off it is one batch run. The Minimal pill used to switch streaming off for the very models built for it, through `live_transcription_enabled` and the overlay style; both `live_transcription_*` settings are gone (a store that still has them loads, the keys are ignored and not written back), and the style now only decides whether the running text is shown. Before the model loads, `ModelTraits::expected` guesses from the model list and assumes no long-form support; the live-decode thread decides again with the loaded model (`ModelTraits::of`). `vad_tail` picks the recorder's trailing-silence tail per recording (`audio_toolkit::vad::VadTail`): 1650 ms for a streaming model (upstream Handy's `VAD_STREAMING_HANGOVER_MS`; with 450 ms every pause between sentences was cut to the same short gap and the model ran sentences together), 450 ms otherwise. A local stream hears exactly that kept speech, like the batch path and like upstream Handy's streams (`FeedKind::Speech`); only a cloud provider's realtime stream gets every raw frame, since its own VAD closes segments at the silence. Fed the room noise around a dictation, Nemotron wrote a 55-second English dictation in Devanagari and Moonshine returned nothing for a short one. `SpeechActivity` still counts only the 450 ms tail as speech (`ACTIVITY_TAIL_FRAMES`), so the longer tail never pushes "Stop after silence" out by a second
  - `transcription/chunked.rs` + `audio_toolkit/chunking.rs` - **Long-form chunking** (`long_form_chunking`, on by default, "Split long recordings" in Settings → Advanced → Performance; upstream Handy #2282). Most models lose accuracy or fail outright past 30-40 s in one run, and the old ONNX Parakeet stopped transcribing at about seven minutes. Audio up to `MAX_CHUNK_SAMPLES` (40 s) is one chunk; longer audio is cut at pauses from Silero's per-frame speech probabilities (`SpeechScorer`) into chunks of about 30 s, no shorter than 5 s. Live (`ChunkSession`) and batch (`decode_clip`) cut the same audio at the same places, because a live cut is only final once `LOOKAHEAD_SAMPLES` past its window are scored, so a live result and a batch run over the recording agree. A chunk that fails or is cancelled sends the recording to the batch path. One deliberate divergence from upstream: audio that cannot be scored is cut at fixed lengths, where upstream decodes the rest in one piece, which is exactly the run that fails on a long recording
  - `transcription/chinese_script.rs` - **Simplified or Traditional Chinese output** (`chinese_script`: `Auto` = as transcribed, `Simplified`, `Traditional`; upstream Handy #2186). `zh-Hans` / `zh-Hant` as the language still convert every transcript, as they always have. Otherwise `script_rule` decides before the text exists: a plain Chinese or Cantonese run converts, a run on another language keeps its text, and a detected-language run converts only if the text reads as Chinese (`looks_chinese`: Han characters, no kana, no Hangul, Han at least half the letters), so a mixed-language user on Auto only has their Chinese touched. Upstream uses `whatlang` for that check; reading the script needs no new dependency and answers the one question asked. Cantonese gets Hong Kong's OpenCC tables, Mandarin Taiwan's. The live preview (`LiveScript`) decides once it has six characters and sticks, so it never flips script mid-sentence. The row only shows where it can change something (`chineseScriptRule.ts::showsChineseScript`, also on the cloud path, since every provider can answer in Chinese), and only for someone it concerns (`offersChineseScript`): Chinese or Cantonese as the language, or on Auto when the app is in Chinese or a script is already chosen. On Auto it used to show on every cloud provider and every multilingual model, a row about a script most people never see

- `managers/language.rs` + `src/lib/languageCodes.ts` - **Spoken-language codes, one rule on both sides.** The app writes Whisper's codes plus `zh-Hans` / `zh-Hant`; model authors write `nb` or `no`, `fil` or `tl`, `zh`, sometimes `en-US`. `canonical_language_code` compares in one form (base subtag, `nb` → `no`, `fil` → `tl`, Nynorsk and Cantonese kept apart), and two functions leave it: `effective_language` answers in the app's vocabulary (the intent when the model lists it, else `auto` when the model detects, else English, else the model's first language) and `engine_language_code` in the model's (`zh-Hans` → `zh`, `no` → `nb`, `None` for auto). **`selected_language` is an intent and is never written back** on a model switch, so switching to an English-only model and back returns to exactly what the user chose; the picker shows the effective language (`LanguageSelector`) and offers Auto only for a model that detects. The TypeScript twin is tested against the same cases; change one, change both. `RunPlan::effective_language` carries the result to text post-processing, and the Models page filter, the "N languages" chip (`ModelLanguages.tsx`) and onboarding all count languages through `uniqueLanguages`, so `zh-Hans` and `zh-Hant` are one language everywhere
- `managers/legacy_models.rs` - **The models from Handy's first catalog and what replaced them**, in one table (`LEGACY_TWINS`) so the loader, the model list and the migration prompt cannot disagree. Each old id has a GGUF twin in the bundled catalog (`replacement_id`: `"<slug>-gguf"`). The two kinds age differently. A Whisper `.bin` still loads through transcribe.cpp, so it stays usable, tagged "Older", and listed only while it is on disk (`speechCatalog.ts::isOffered`), because two rows with one name read as the same model twice. An ONNX model (Parakeet V2/V3, Moonshine, SenseVoice, GigaAM, Canary, Cohere) is **retired**: its engine is gone (it ran on DirectML on Windows, which is where issue #82's crash lived). A downloaded one is kept on disk, never loaded, tagged "Retired" with "Get new version", and gathered in a notice above the catalog with one "Delete old files" action; one that is not downloaded is not offered at all. `ModelInfo.is_legacy` / `is_retired` / `replacement_id` are stamped at the read accessors (`stamped`), `ensure_selectable` refuses a retired model as the selection, and `legacy_download_refusal` refuses to download any legacy id. **A retired model can stay the selection after an upgrade**, on purpose: silently switching to another model would hide that this one has a new version. `speech_readiness` reports it as `NeedsUpdate`, `useModelSlots` as `needs_update` (the sidebar reads "Needs update"), Home and the Models page's speech tab show `RetiredSelectionPrompt`, the main shell opens `RetiredSelectionDialog` (a pop-up when the app opens; nothing downloads until the user presses Download new version, because a new version is up to 1.8 GB; "Later" closes it until the next launch or until `SPEECH_UPDATE_EVENT` reopens it, `speechUpdate.ts::dialogClosed`), and every surface that offers the new version goes through `useReplaceRetired` over the pure `retiredReplacement.ts`, so they agree on what the button says and does. When the retired model is the selection, its replacement is selected the moment its download lands. Onboarding preselects the replacement instead of marking the retired model "In use" (`setupStartingModel`), and a freshly downloaded legacy or retired model is never auto-selected (`isAutoSelectable`)
- `managers/history.rs` - Transcription history storage, and the **recording-retention policy**. `resolve_retention_plan(period, limit, custom_days, now)` is a pure function returning a `RetentionPlan` (`KeepAll` / `ByCount` / `OlderThan`) — the clock is a parameter so every branch is unit-testable, because every bug this feature had was in the decision rather than in the SQL. `apply_plan` prunes in **one transaction on one connection** and unlinks WAVs only after the commit, and only once no surviving row references them; it previously opened a second connection and committed once per row, so a `SQLITE_BUSY` against the concurrent insert in `save_entry` failed the settings command _after_ the value was already written. `count_pending_deletions` is the dry run the UI uses to say "this deletes N recordings" before anything is destroyed. Three months means three **calendar** months (`chrono::Months`), not the `3 * 30` days the old code used and admitted was approximate. Enforcement happens at four points, not one: launch, a 30-minute sweep in `lib.rs`, after every `save_entry`, and when the History panel mounts (`enforce_recording_retention`) — with only the first two, an age policy never fired on a machine where the app stays open and no new dictation lands, so entries crossed their cutoff and stayed listed, which reads as the setting doing nothing. The History list keeps one row per id (`historyFeed.ts`: `prependHistoryEntry` / `appendHistoryPage`, Handy #2256), because the first page can load after a row is saved but before its "added" event arrives, and both used to list it
  - `local_models.rs` - Registering models the user **already has on disk**, so an existing collection or a self-made fine-tune needs no re-download and no hand-copying (issue #18). Two entry points, one destination: pick a file, or link any number of folders (`settings.model_folders`) that are then scanned recursively (`scan_folder`, bounded by `MAX_SCAN_DEPTH` / `MAX_SCAN_ENTRIES`, symlink-loop guarded). The hard part is **classification**, and it is done by content rather than filename, because a bare `.gguf` doesn't say whether it's speech-to-text, a chat model, or a vision projector that isn't a standalone model at all: `classify_model_file` reads `general.architecture` from the GGUF header (via `gguf_meta`) and routes an arch in `model_capabilities::KNOWN_ARCHES` to `TranscribeCpp`, a `clip`/`mmproj` arch to a projector (rejected on its own, auto-paired when it sits beside an LLM), and anything else to `LlamaCpp` — an unknown arch is far more likely to be a new chat model than a broken file. A `.bin` is validated against the ggml magic and registered as `EngineType::Whisper`, which loads through transcribe.cpp exactly like a GGUF (the engine type only says the file is a whisper.cpp `.bin`; it picks no other engine). On the `model.rs` side, `ModelInfo.local_path` / `local_folder` carry the result and every path-resolution site (`get_model_path`, `update_download_status`, `apply_gguf_header_hints`, `resolve_mmproj_path`, `local_llm::gguf_path_for`) reads the user's path instead of `<models_dir>/<filename>`. The standing invariant: **these files are not ours** — registering copies nothing, `delete_model` only unregisters, and a folder-derived entry refuses individual removal (the next scan would re-add it) and points at unlinking the folder instead. Only individually picked files are persisted (`local_models.json`); folder contents are re-derived on every scan so a model added to or deleted from a linked folder appears or disappears on its own
- `audio_toolkit/` - Low-level audio processing:
  - `audio/` - Device enumeration, recording, resampling
  - `ducking/` - **Other audio while recording** (`audio_ducking`: Off / Lower / Mute, and `audio_ducking_amount`, 10–90%, for Lower; "Settings → Audio → Other audio"). It replaced the `mute_while_recording` switch, whose on becomes Mute at load (`settings::migrate_mute_while_recording`). One worker thread (`Ducker`) does every volume change in order, because the tools are slow (`osascript` on macOS, `pactl`, then `wpctl`, then `amixer` on Linux, all run with `LC_ALL=C` and without the AppImage's `LD_LIBRARY_PATH` entries (`helpers::appimage`); `pactl` scales every channel so a sink's balance is kept, `wpctl` cannot) and a fade takes 300 ms down and 200 ms up; Windows uses `IAudioEndpointVolume` on the default render endpoint. It puts back only what it changed, on the device it changed (the Windows endpoint, the Linux node or sink, and the macOS default output device, by its CoreAudio id, are pinned), leaves a volume the user moved meanwhile where they put it (`MOVED`), and leaves output that was already muted or silent alone. `AudioRecordingManager` gates it: `try_start_recording` arms the gate, `quiet_other_audio` runs after the start cue, and `restore_other_audio` (every stop, cancel and microphone close) disarms it, so a quieting that lands after a quick tap does nothing. The old mute had no gate and was not undone by a cancel while the microphone stayed open, so either left the computer muted. Stop cues wait for the restore on their own thread (`actions::play_stop_cue_after`), never the transcription. The "Lower by" slider previews on whatever is playing (`preview_audio_ducking`, `Owner::Preview`): it holds for 1.5 s after the last change, a recording that starts takes it over, and it is ignored during a recording. `release_before_exit` restores anything still quiet
  - `vad/` - Voice Activity Detection (Silero VAD). `SmoothedVad` marks each pre-roll frame once it has gone out (`BufferedFrame::emitted`): hangover frames stay in the pre-roll buffer, so speech resuming within the prefill window used to replay up to ~0.45 s the recording already had, and the model transcribed it as repeated words
- `commands/` - Tauri command handlers for frontend communication
- `cli.rs` - CLI argument definitions (clap derive)
- `shortcut/mod.rs` - Global keyboard shortcut handling (two engines: `handy-keys` and the Tauri global-shortcut plugin). Both engines route through the shared `shortcut/handler.rs::handle_shortcut_event`, which resolves the recording mode via `transcription_coordinator::recording_mode`. Dictation (with or without cleanup) and the ask are each held or tapped on their own setting (`push_to_talk`, `assistant_push_to_talk`; `settings::holds_to_record`): on means hold to record, off means tap to start and tap to stop. They used to share `push_to_talk`, which made hold-to-dictate with tap-to-ask impossible; a store from before the split gives the ask the shared value (`split_recording_modes`), so nobody's ask changes on update. The call has no mode: it is a press to start and a press to hang up. A held dictation can also turn hands-free mid-hold (`hands_free.rs`); the ask cannot. **The defaults are one scheme on every platform**: two keys to dictate (Windows Left Ctrl + Win, macOS Fn, Linux Ctrl+Space), two to ask (Left Ctrl + Left Alt, Fn+Ctrl, Ctrl+Alt+Space), the dictation keys plus Shift to dictate and clean up, the ask keys plus C to start a call, and Esc to cancel. Linux has a main key in every combo because its default engine (Tauri's plugin) cannot register a modifier-only one. The Windows ask has to contain Ctrl: the ask harvests the selection with a synthetic Ctrl+C while the keys are still held, which only works because Ctrl is already part of that combo and the other key is withheld from Windows. **Shortcuts that share their first keys (Ctrl+Alt and Ctrl+Alt+C; Fn and Fn+Ctrl) are resolved in two places, one per recording mode.** With Tap to toggle, the vendored handy-keys manager fires modifier-only hotkeys when their keys are _let go_ (`HotkeyManager::set_fire_on_release_for`, per hotkey: each shortcut's own setting is applied when it registers and again by `handy_keys::apply_recording_mode` when either setting changes; every shortcut that does not record, the call among them, fires on release, which only matters for one made of modifiers alone): letting go with nothing pressed in between is the tap, and any other key in between was another shortcut, so that one never fires. Held and tapped hotkeys can share keys (a Mac's held Fn to dictate, tapped Fn+Ctrl to ask): a tapped one that extends a held one takes over from it the way a held one does, so within the window the held one is withdrawn and the tapped one waits for its keys to be let go, and past the window the held one owns the keyboard. There is no timer, which is why it holds however slowly the C follows; a fixed 200 ms grace was tried first and a deliberate Ctrl, Alt, pause, C beat it every time, so every call still opened the ask's panel on the way. With Hold to talk the press has to start recording at once, so the manager fires on press and withdraws the hotkey with `HotkeyState::Cancelled` when a keyboard key follows within `CHORD_CANCEL_WINDOW` (400 ms); `handle_shortcut_cancelled` turns that into a coordinator `Abort` that discards the recording without an Undo offer (`utils::discard_aborted_recording`). What such a press would _show_ waits for that window (`shortcut/chord.rs`: `holds_back` when another live shortcut extends this one's keys, `reveal_when_settled`, `reveal_now` on release, `forget` on withdrawal), so the recording runs from the first moment but its pill or panel never flashes up on the way to another shortcut. That is also why ending a running call is part of the ask's reveal rather than its press: the call key starts with the ask's keys, and ending the call on the press meant the call key could never hang up. The Windows hook then replays the modifiers it had withheld in front of that key (`replay_chord`), so VS Code gets Ctrl+Alt+↑ and a German layout gets Ctrl+Alt+Q = `@` instead of Ctrl+Q; and when it blocks the last modifier of a combo whose earlier Win or Alt Windows did see, it taps the unassigned vk 0xE8 so releasing that key opens no Start menu or menu bar. Its own injections carry `OWN_INJECTION_MARKER` and pass straight through. **Cancel, the call and the hands-free key are removable** (`settings::OPTIONAL_BINDINGS`). A shortcut row at rest shows only its keys; clicking them opens the editor, which is the only place "Use default" and, for these three, "Turn off" appear (`ShortcutEditActions`), so neither can be hit by accident, and turning off is announced with an Undo. Esc is not how the editor closes, since Esc is itself a key you may want to record; clicking elsewhere leaves it unchanged. Dictation and the ask always keep a key. An empty Cancel is only migrated to Esc once, from installs that predate the Esc default, so a removed Cancel stays removed. `migrate_binding_defaults` moves any binding still on an older default to the new one, except on macOS, where an install still on the old Option-based defaults keeps them (`keeps_previous_default`), because the Fn key needs "Press 🌐 key to" set to Do Nothing first; the Home shortcuts card says so when it is not (`globe_key_has_own_action`). The handler also routes the cancel/`Esc` binding to either an active recording or a busy assistant reply. **Cancel is registered for a recording through `CancelReconciler`** (one per engine, `handy_keys::CANCEL` / `tauri_impl::CANCEL`): start and stop only record what they want, synchronously and so in order, and each spawned task applies the latest request against what the engine really holds. Two spawned register/unregister tasks have no order, and after a very short recording the unregister could run first and leave Esc taken from every app until the next recording. **A shortcut can have other keys** (`ShortcutBinding.alternate_binding`, added from the editor's "Add another"): both sets are registered under the binding's own id, so the coordinator, Cancel and the chord hold-back treat them as one shortcut, and a recording started with one stops with the other. What each engine listens for is `shortcut/combos.rs::armed` (own keys first; other keys only while the own keys are set; a mouse button only with `mouse_button_shortcuts` on, only on the SpeakoFlow Keys engine, never left or right click), registered own-keys-first by `arm_with`, so a failure of the own keys registers nothing and a failure of the other keys leaves the shortcut on its own. The handy-keys engine maps one binding id to several hotkey ids and unregisters by id; `chord.rs` counts every live set of keys, a shortcut's own other keys included, as a longer shortcut. **Mouse buttons (Experimental)** are hotkeys like keys: the vendored hooks keep a registered middle, Back or Forward button from the app under the pointer (`platform::state::swallow_mouse_button`, decided on the press and mirrored on the release, so an app never sees half a click), and the manager takes a registered button pressed on top of a held modifier-only hotkey as a chord rather than as an ordinary click. The Linux engine reads only left, right and middle (as rdev's grab did before it), so the middle button is the only one a Linux shortcut can use. **A mouse button is only ever a shortcut's other keys, never its own** (`combos::own_keys_refusal`, enforced in `change_binding`): the first version let one replace a shortcut's own keys, so pressing Back in the editor turned Ctrl + Win into Back alone, and turning mouse buttons off then had to put the default keys back behind the user's back. Now a button pressed while recording a shortcut's own keys is saved as its other keys and the own keys stay as they were (`HandyKeysShortcutInput`; refused with a pointer to click them when the other keys are already keyboard keys someone chose, and on a shortcut that is turned off, since other keys are only listened for while own keys exist). Turning mouse buttons off therefore changes no shortcut, only what is listened for. An install from that first version is repaired once at load (`settings::move_mouse_buttons_to_other_keys`): the button moves to the other keys, swapping with keyboard other keys so nothing is lost, and only gives way to the default when both slots were buttons
- `managers/local_llm.rs` - Bundled llama.cpp sidecar. **Two engine instances, one per `LlmRole`**: `Assistant` (port 11435, vision projector, full context) and `Cleanup` (port 11436, no projector, context capped at `CLEANUP_CONTEXT_SIZE`, `LLAMA_ARG_THINK_BUDGET=0`). Sharing one engine meant a different model on either side evicted the other on every use. **Both roles take the GPU** (`ALL_GPU_LAYERS`): cleanup used to pass `-ngl 0` for small models because a cold load is ~2x faster on CPU and skips the one-time 13–20s shader compile, but that optimised the wrong half — measured on a 2B Q8*0, generation runs at ~212 tok/s on a dedicated GPU against ~21.8 tok/s on the CPU, and generation is what happens on every dictation, while the load happens once behind `warm_up()`. Device \_selection* is pinned with `--device`, not `--main-gpu`: the latter does not choose where the model runs (measured on a 4070 Ti SUPER + Ryzen iGPU box, `--main-gpu 1` still ran on the dedicated card), so on any machine whose ggml device 0 is the integrated GPU the engine silently ran there at ~7 tok/s. `pinned_device_arg` / `select_engine_device_arg` resolve the flag from the engine's **own** `--list-devices` output (`parse_engine_devices`, cached per run) matched against our probe by adapter description, because the two enumerations are independent and their order need not agree. To bump the pin, check every archive exists in the new release and re-test chat, vision, tool calls, JSON-schema output, `LLAMA_ARG_THINK_BUDGET=0` and the `--list-devices` format; every install re-downloads once because `engine.tag`, which records the tag of the archive actually unpacked, no longer matches. That re-download never costs a working engine: the new build is unpacked into `models/.engine-new/` and swapped in (`swap_in_engine`: old build moved aside to `models/.engine-old/`, new one moved in, old one deleted last), and when it cannot be downloaded or moved in the old engine keeps running and the next start tries again. `HANDY_LLAMA_RELEASE_TAG` overrides the pin and `HANDY_LLAMA_SERVER` bypasses the managed engine. The engine logs at trace level (`LLAMA_ARG_LOG_VERBOSITY=4`: layer offload, buffer sizes and the scheduler's split count, about 30 lines per request, no prompt text) and also to its own file (`LLAMA_ARG_LOG_FILE`, `llama-server[-cleanup]-debug.log` beside the console capture), both set by env var so a build that predates them still starts; a start failure quotes the console tail plus any lines only the engine's own file has

- `stt_cloud.rs` - **Cloud speech-to-text**: transcription on a hosted API instead of a local model, gated on `SttEngineMode::Cloud` (default `Local`, so an existing install is untouched). Five services ship configured plus a free-form OpenAI-compatible entry, and `CloudSttKind` is a real protocol dispatch rather than a label — "OpenAI-compatible" is near-universal for chat but not for transcription: ElevenLabs authenticates with `xi-api-key` and calls the field `model_id`, Deepgram takes the audio as a **raw request body** with every option as a query parameter and no multipart envelope at all. Two decisions carry most of the weight. First, requests run on a **dedicated thread with their own current-thread runtime** (`block_on_request`), because `TranscriptionManager::transcribe` is synchronous and its callers straddle the runtime boundary — `actions.rs` calls it from inside an async task while history and voice-conversation come in via `spawn_blocking` — so neither `tauri::async_runtime::block_on` nor `reqwest::blocking` is safe under both. Second, an incomplete cloud configuration resolves to `Err` and **falls back to the local engine** instead of failing the dictation; only a _complete_ configuration that then fails on the wire surfaces an error, because at that point there is no loaded local model to fall back to. `batch_model_id` maps `scribe_v2_realtime` → `scribe_v2` so the batch fallback still works for a user configured for streaming, which is exactly when the fallback matters. Custom words are forwarded as provider-native biasing (ElevenLabs `keyterms`, OpenAI `prompt`, Deepgram `keyterm`), and when they are, the local fuzzy-correction pass is skipped — a second pass over text the model already got right can only corrupt it
- `stt_cloud_stream.rs` - Realtime cloud STT over WebSockets (ElevenLabs Scribe v2 Realtime, Deepgram). `CloudStreamSession` is a deliberately **blocking facade** owning its own current-thread runtime, so it drops into the transcription manager's existing `feed`/`finalize` worker shape instead of forcing an async rewrite; the socket needs no background pump because `feed()` is called ~30x/sec and drains what has already arrived via `now_or_never()`. ElevenLabs runs with `commit_strategy=vad` so segments close at natural pauses — that is what produces an append-only committed prefix instead of one enormous commit at the end — and the final flush sends the tail with `commit: true`. Provider partial/committed events map onto the overlay's existing `committed`/`tentative` split, published through a `LiveTextSink` closure rather than an `AppHandle` so the protocol logic has no dependency on the window layer (and can be driven by a live test). Streaming support is checked against the **model**, not just the provider, because ElevenLabs' realtime and batch endpoints have separate model namespaces. A partial can arrive after the commit that closed its segment, and taken at face value it became the new tail, which is how two dictations were pasted with the whole transcript repeated, the second copy ending in an earlier guess. `LiveTranscript` drops a partial that repeats the segment just committed, judged by order-aware word overlap, and never drops a commit, since someone who says a sentence twice means it twice. Every failure is non-fatal and answers `None`, routing `finalize_stream()` to the complete batch transcription. **Amazon Transcribe is the one provider with no batch endpoint** (its batch API needs an S3 upload and a polled job), so it always streams — `streams_only` overrides "Transcribe as I speak" through `stt_cloud::streams_live` — and its batch path (a failed live session, a call's utterances, History, meetings) replays the recording through a fresh stream paced at speaking speed (`transcribe_by_streaming`): AWS processes a stream in real time and its own SDK asks for recorded audio to be rate-limited to that, so a replay takes as long as the recording. There is no AWS SDK. `stt_aws.rs` presigns the WebSocket URL with SigV4 (tested against AWS's published presigned-URL example; the signed `host` includes `:8443`, which tungstenite also sends in `Host`) and speaks AWS's binary event-stream frames (CRC32-checked; an empty `AudioEvent` ends the stream, after which AWS sends the last results and closes the socket itself, which is what finalize waits for). The generic slots carry AWS's shape: the key slot holds `KEY_ID:SECRET[:SESSION_TOKEN]`, composed by the Settings card (no part can contain a colon), and the editable endpoint slot holds the region. AWS wants full locales and auto-detects only among the candidates it is given (`streaming_language`: the app language first, then common languages, five in all); a language it cannot stream in the chosen region resolves to `CloudSttUnavailableReason::UnsupportedLanguage` instead of reaching another language's model. The presigned URL carries the signature and any session token, so only its host is ever logged
- `stt_cloud_live_tests.rs` - `#[ignore]`d live checks against a real ElevenLabs key (batch, realtime, the verification probe, and the bad-key message). Offline unit tests can only prove this app parses what it expects; whether the endpoint accepts what it _sends_ has one authority. The key comes from `ELEVENLABS_API_KEY` or the app's own keychain slots, and the audio from the newest saved recording, so `cargo test --lib stt_cloud_live -- --ignored --nocapture` needs no setup on a machine that already has ElevenLabs configured

Two traps worth knowing before touching the cloud-STT settings UI. First, **`updateSetting` is an allowlist, not a generic writer**: `settingUpdaters` in `src/stores/settingsStore.ts` maps a settings key to the command that persists it, and a key with no entry updates the store optimistically and then only `console.warn`s — the value looks saved and evaporates on the next refresh. Every `cloud_stt_*` field therefore goes through its own command (`set_cloud_stt_provider` / `_model` / `_base_url` / `_streaming` / `_send_custom_words` / `_no_verbatim`), per-provider rather than whole-map so two edits cannot clobber each other's provider. Second, **every wait in `stt_cloud_stream.rs` must be bounded**: `feed()` runs on the thread draining the audio channel, so an unbounded `block_on` leaks that thread and the socket. Note also that `now_or_never()` is the wrong way to poll this socket — a future that is never `Pending` means `block_on` never parks, and a current-thread runtime only ticks its I/O driver on park, so a "non-blocking" read can report nothing while data sits waiting; `DRAIN_POLL` is small but deliberately non-zero.

**OpenRouter needs two registry fields, not a new protocol.** It reaches ~20 transcription models (Whisper, GPT-4o-transcribe, Deepgram Nova-3, Google Chirp 3, MAI-Transcribe, Voxtral, Parakeet, Qwen ASR, Grok STT) behind one key and accepts the OpenAI multipart shape, so `CloudSttKind::OpenAiCompatible` covers the wire format. `models_endpoint` carries the discovery path **including its query string**, because OpenRouter excludes transcription models from the default `/models` catalog and only returns them for `?output_modalities=transcription` — a bare `/models` there lists hundreds of chat models and not one that can transcribe. A listing already scoped that way also skips the `looks_like_transcription_model` name heuristic, which would otherwise drop correctly-listed models whose slugs say nothing about the task. `honors_keyterms` is false for OpenRouter because it documents `prompt` as accepted-but-ignored on the multipart route: without that flag the app would believe it had biased the request upstream, skip its own fuzzy custom-word pass, and apply neither correction. Slugs there are namespaced `vendor/model` and must not be rewritten. `ensure_cloud_stt_defaults` also normalizes provider **order** to the shipped registry, so a store upgraded across versions doesn't show a new provider appended after "Custom" while a fresh install shows it before.

**Cloud transcription latency is connection setup and a cold provider route, not upload.** Measured against OpenRouter from Nepal (`stt_cloud_bench`, all `#[ignore]`d): WAV encoding is 12 ms and client construction 0.4 ms, both irrelevant. Latency does **not** scale with payload — a six-length least-squares fit on `mai-transcribe-2` put the uplink at ~1.5 MB/s, i.e. 0.02 s per second of speech, so even a 60-second dictation spends about a second uploading on a fast link. That held for a desktop on wired broadband and did not hold on a laptop: on a ~1 Mbit/s Wi-Fi uplink a five-minute WAV (9.6 MB) took ~77 s to upload, longer than the fixed 60 s timeout, so long dictations to batch-only providers (Azure MAI-Transcribe) fell back to the local model. Batch uploads are therefore **48 kbit/s MP3** (`encode_mp3_16k_mono`, LAME via `mp3lame-encoder`, 5.3x smaller; measured as no WER change against WAV on 6,559 LibriSpeech words) for every hosted provider, and WAV only for the custom endpoint and for a route that answered MP3 with a media-format error (`is_format_rejection` → `remember_mp3_rejected`, process-lifetime, and the same recording is resent as WAV). The request timeout also scales with the audio (`request_timeout`: `cloud_stt_timeout_secs` + 0.5 s per second of audio, capped at 30 min), with a separate 10 s `CONNECT_TIMEOUT` reported as "Could not reach" so it gets the transient retry; the timeout is per request, not baked into the pooled client, so one pool serves every recording length. Two things did matter. First, `block_on_request` built a **fresh thread, runtime, and `reqwest::Client` per request**, which makes keep-alive impossible: a pooled connection belongs to the runtime whose I/O driver services it, so tearing that runtime down discarded the connection. There is now one process-lifetime multi-threaded runtime (one worker, which keeps polling the I/O driver between dictations so an idle connection survives the gap) plus a client cache keyed on base URL + key + timeout, with a 300 s idle timeout and TCP keep-alive; an interleaved 5-round A/B measured median 2.65 s fresh against 1.93 s pooled (~715 ms, 27%). Second — and larger — **the provider's route to the upstream model goes cold, and only a real transcription warms it**. A benchmark loop keeps that route hot; a person dictates once every few minutes and pays for it, which is why the app's log showed 3.5 s and 4.3 s for two real dictations while ten interleaved back-to-back rounds measured a p50 of 1.19 s. Across three runs with 4-minute idle gaps, no warm-up gave a 3.24 s median against 1.81 s after a single 0.25 s transcription first — ~1.4 s, ~44%, never worse. So `prewarm_cloud_stt` sends a **quarter-second tone through the ordinary transcription path** at recording start rather than the authenticated `GET /models` it used to send: that GET warmed DNS/TCP/TLS, none of which was the problem (the log confirms no new connection was opened before the `POST`). Cost is fractions of a cent per cold dictation, it is fire-and-forget, and `ROUTE_WARM_FOR` skips it when a real request finished within 30 s — biased heavily toward warming, because a redundant warm-up costs a quarter-second of audio and a skipped one costs the user two seconds. The warm-up is itself a cold request (~2.3 s), so it needs to fit inside the recording: at 4 s of speech one round gained 1.9 s and another only 0.4 s. One thing was measured and deliberately **not** done: hedging a duplicate request against the ~3 s tail (the spikes hit a bare client and the app's client in the _same_ round, so they are correlated provider-side stalls a duplicate does not escape). Compression was on that list too, for a fast uplink, and came off it when a slow one turned up (above). The residue beyond all this is round-trip distance; only a realtime WebSocket removes it by uploading during speech, which is why ElevenLabs `scribe_v2_realtime` feels immediate and OpenRouter, which has no realtime endpoint, cannot. Chunking a batch provider's audio during recording would buy live text but almost no latency, precisely because latency is flat in audio length. Latency on this path varies by a second run to run, so measure with repeats and medians — single samples have already produced three wrong conclusions here.

**Language is a source hint everywhere; translation only reaches English, and only on one schema.** `selected_language` is shared with the local engine and reaches every cloud provider as a recognition hint (`language_code` on ElevenLabs, `language` on the OpenAI schema and Deepgram) — the transcript still comes back in the language spoken. `cloud_language_code` strips script and region subtags on the way out, because the app's list carries `zh-Hans`/`zh-Hant` for the local variant conversion and no cloud endpoint here understands them; the Simplified/Traditional conversion still happens locally afterwards, and so does the `chinese_script` preference, which on the cloud path judges the intent itself because a provider lists no languages (`chinese_script::script_rule` with an empty list). **No cloud transcription API translates into an arbitrary target language** — not ElevenLabs, not OpenRouter, not Deepgram, not OpenAI — so "speak English, get Nepali" is not a thing any of them offer. English is the one exception and only on the OpenAI schema, whose separate `/audio/translations` route has its output language fixed to English; `CloudSttProvider::supports_translation` marks the providers that have it (OpenAI, Groq, and the custom entry, since self-hosted Whisper servers implement it) and `ResolvedCloudStt::translate` is the conjunction of that flag and the user's switch, so `transcribe_openai` can pick the route without re-deciding. A provider without the route logs a `warn!` naming itself and transcribes normally, and its settings have no Translate to English row at all: the row used to stay, greyed out with a paragraph on why it could not work, and read as broken. On the local side the completion line only says `(translated)` when the engine was actually asked _and_ can do it (`RunPlan::translated`: the switch, a model whose capabilities list translation to English, and a language in use that is not already English) — reading the setting alone made the log assert a translation that never happened, which is how a Japanese transcript came out of a run logged as "translated".

**Filler removal is one switch, not two.** `filter_transcription_output` (`audio_toolkit/text.rs`) used to run on every transcription with no off switch, so `cloud_stt_no_verbatim` only controlled the _provider-side_ flag — which several providers don't implement — and a user who turned it off still got their "um"s deleted. On the cloud path the setting now gates both layers: on asks the provider and runs the local filter as the backstop, off means verbatim. The local engines still filter unconditionally, as they always have. That filter also repairs the seams its own deletions leave (`repair_removal_seams`): removing a filler that opened a sentence used to produce `right? for example` — a lowercase sentence start — and two consecutive fillers left a doubled comma. Casing is repaired after `?` and `!` but never after `.`, because a full stop is also an abbreviation mark and `e.g. foo` must not become `e.g. Foo`; the first character of the transcript is left alone too, since dictation is frequently a mid-sentence continuation. The one exception is a capitalised filler (Handy #2157): the speech model capitalised it because it heard a sentence start, so deleting "Um," from "Um, so I think" hands its capital to the next word, after a full stop or at the very start alike. A lowercase filler hands nothing over, which keeps `e.g. um foo` as it was, and neither does one followed by a word with a capital of its own (`Um, iPhone` stays `iPhone`); `¿` and `¡` open a sentence too.

**A batch fallback changes the model, and the models disagree.** `scribe_v2` and `scribe_v2_realtime` are separate models with separate namespaces, and `batch_model_id` maps the realtime id onto its batch sibling so the fallback still works. Measured on one recording: batch gave "I guess it can do multiple languages… My Transcribe 2", realtime gave "I can just kind of do multiple languages… MyTranscribe2". So with streaming on, a socket hiccup produces materially different wording from the run before it — the substitution is logged at `info!` for exactly this reason. Turning "Transcribe as I speak" off pins every recording to `scribe_v2`, which is the lever to pull when comparing outputs.

- `assistant.rs` - Assistant turn pipeline (`run_assistant_turn`): LLM chat, screen vision, profiles/personas, per-profile response-length. Runs a bounded tool-calling loop (`llm_client::send_chat_stream_with_tools`, `tool_choice = "auto"`, max ~3 rounds) exposing `build_assistant_tool_capabilities()`. **The tool list is never empty**: `get_current_datetime` plus `set_reminder` / `list_reminders` / `cancel_reminder` go out on every turn, with `web_search` and `capture_screen` added only when their feature is on. The clock used to sit behind the web-search flag, which was wrong on its own terms and became a bug once reminders existed — "remind me at nine tomorrow" cannot be resolved without knowing what today is. Making the list unconditional needs one safety net, since a provider that rejects a `tools` array would now fail _every_ message rather than only web-search users': `is_tools_unsupported_error` plus a single no-tools retry (`tools_fallback`), guarded on nothing having streamed yet so a mid-reply failure can never restart a turn the user is reading. Injects the advisory personal-memory block late in the prompt and triggers offline memory distillation when a conversation ends. **Panel window lifecycle is main-thread-only:** `build_assistant_panel` / `present_assistant_panel` are private and every public entry point (`create_assistant_panel`, `show_assistant_panel`, `destroy_assistant_panel`) queues them via `run_on_main_thread`. Shortcut actions run on the keyboard engine's thread, and building a WebView window from there deadlocks the event loop — the whole app then freezes (no overlay, no dictation, undraggable windows). Queuing also keeps a create ordered behind a destroy, so a fast off → on of the master switch cannot leave the app believing in a window that is gone. **The quick ask is one fixed, transparent frame per show** (`ask_placement` / `ask_placement_on`): its size is the largest the answer card may grow to (display fraction by dock zone, clamped; the old size preset is gone — it only moved the ceiling of an invisible frame), it is placed at the dock zone on the display from `assistant_ask_display` (default `cursor`; the old `last_used` is migrated) on **every** show, and it never resizes or moves while an ask runs — the webview morphs a pill into the card inside it and `hitRegion.ts` passes the rest of the frame through. `assistant-ask-layout` tells the webview which edge of the frame is flush with the screen. This replaced a pill-sized window that faded out, waited, resized-and-moved, measured the card and faded back in, which is why answers could only appear once complete, and four stored positions (`LEGACY_POSITION_KEYS`, deleted on launch) that made the panel open somewhere different each time; only a live call remembers where it was dragged. **On Windows the quick ask does not take the foreground** (`ASK_KEYBOARD_ON_SHOW`): a voice ask harvests the selection with a synthetic Ctrl+C at the moment the hotkey goes down and Insert pastes back into the same field, so a panel that activated on show broke both; it is `WS_EX_NOACTIVATE` until the text field asks for the keyboard (`assistant-ask-keyboard` → `set_panel_keyboard`). Every quick ask starts from an empty conversation (`should_reset_quick_ask`) and hiding the panel clears it — there is no follow-up field; History's Continue opens the call instead (`continue_in_call`)
- `reminders.rs` - **Reminders**: "remind me to send that invoice in twenty minutes". A tool the model calls rather than a form the user fills in, so the whole interaction is one spoken sentence — and because the assistant can already see the screen, "look at this and remind me about it later" needs nothing extra. Three properties are what make it trustworthy rather than a toy. **A reminder outlives the app**: it is written to `reminders.json` on creation, and anything that came due while the app was closed fires on the next launch (`partition_due` treats "due a second ago" and "due yesterday" identically) — an alarm that only works if you never quit is one you stop checking. Something that fired and was never acknowledged is re-presented **once** at startup, not on every tick, because the popup's X exists so a reminder can be set aside without being marked done. **It arrives without stealing your work**: the popup is the recording overlay's discipline applied to a notification — always on top, `focused(false)`, and `focusable(false)` on Windows only (`WS_EX_NOACTIVATE`), since on macOS a non-activating window makes WebView buttons unreliable and Done/Snooze are the entire point. **It does not go away on its own**, and several due at once stack in one window rather than opening one each. Every scheduling decision is a pure function with the clock as a parameter (`resolve_due_at`, `next_wake`, `partition_due`), so the logic is unit-testable without sleeping; the scheduler is its own thread parked on a channel `recv_timeout` (woken by any change, capped at a 60 s poll so a laptop resume or a corrected system clock costs one interval rather than the whole delay) rather than a tokio task, which a long sleep would occupy. `resolve_due_at` reads a naive `at` as **local** time (what "at six" means) and refuses a past or sub-5-second time with a sentence the model can relay, because firing immediately interrupts the sentence the user is still speaking and silently moving it to tomorrow hides a wrong answer behind a right-looking one
- `insights.rs` - **Insights**: everything the app counts about how it is used, read in one go (`get_insights`) for the Insights page, Home's numbers and the share card. Each feature keeps **lifetime counters beside its own data**, never derived from rows at read time, because every source of rows shrinks: dictation in `usage_daily` (history pruning), the assistant in `assistant_usage_daily` (the conversation list is capped at `ASSISTANT_SESSION_CAP` and can be cleared), meetings in `meetings.db`'s `meeting_usage` (one row per meeting ever recorded, no foreign key, so deleting a meeting's hour of audio does not take it out of the totals). The assistant is counted where a question enters the conversation (`insights::record_question` from `run_assistant_turn` and the cat turn: a quick ask, or a turn on a call) and a call once, with its length, when it hangs up (`voice_conversation::end_session`, only a call something was said on, capped at six hours). Existing conversations and meetings are folded in once (`backfill_assistant_usage` behind its own `usage_meta` key, migration 3 of the meetings store), at init before anything can record, so nothing is counted twice. - `llm_client.rs` - Shared OpenAI-compatible chat client used by the assistant, post-processing, and remote TTS: SSE streaming, tool-calling (the web-search path), structured/JSON-schema output, model listing, provider auth (Anthropic `x-api-key`, Azure `api-key`, OpenRouter `HTTP-Referer`/`X-Title`), Azure base-URL normalization to `/openai/v1`, and system-prompt folding for the built-in local engine (Gemma-style templates that reject a `system` role). Two invariants here exist because a **conversation can be silently bricked** otherwise. First, `enforce_alternating_roles` runs for **every** provider, not just the built-in engine: a strict chat template is a property of the model, not of who serves it, and Gemma on a cloud gateway rejects two consecutive `user` messages with HTTP 400 "Conversation roles must alternate" exactly like the local template does. Our own history produces that shape routinely — a voice barge-in cancels generation before the first token, so the user message is recorded with no assistant message after it — and because the offending pair stays in the conversation, _every_ later turn failed identically until the conversation was cleared. Dropping content-free assistant turns and merging adjacent same-role ones repairs the request at send time (a no-op on a well-formed conversation), so even a history already corrupted on disk works again. Second, an error the provider delivers **inside a 200 SSE stream** (`data: {"error":{…}}`, which is how Bedrock reports a rejected body) is parsed as `StreamErrorEnvelope` rather than skipped as a malformed frame: it used to be logged at debug and the round resolved to an empty answer, so the user got silence with no error anywhere. A mid-stream error that arrives _after_ tokens is logged and the partial reply kept, since dropping it would blank text already on screen

- `tts.rs` - Spoken answers (Kokoro local / OpenAI-compatible / ElevenLabs / Azure AI Speech). Only the `kokoro` engine synthesizes **inside the assistant WebView** (`src/assistant/useKokoroTts.ts` + `kokoro-js`): ~310 MB of fp32 ONNX weights, and on WebGPU a second copy as GPU buffers. Because the panel window is created at launch and only ever hidden, that used to be resident for the app's lifetime — and it loaded even for users on a remote engine. `src/assistant/localTts.ts` now holds the policy shared by the panel and Settings: load only when the selected engine is local (`localTtsActive`), prepare only while the panel is actually on screen, and release the session after an idle window (60 s hidden / 10 min visible) unless speech is in flight (`isSpeechInFlight`). - `audio_tags.rs` - **ElevenLabs audio tags** (`[laughs]`, `[whispers]`, `[applause]`), which Eleven v3/v4 act out or play as sound effects instead of reading. Stripping is needed even with the feature off, because tags written during an ElevenLabs call stay in the conversation history and a model imitates its own earlier replies after the user switches voice. The sanitizer therefore takes a `keep_audio_tags` flag (`sanitize_for_speech_for`, `sanitize_for_speech_chunk(_, keep)`, `SpeechChunker::keeping_audio_tags`), and `strip` is deliberately narrow — lowercase start, letters only, not glued to a word — so `[Ctrl]`, `[1]`, `[x]` and `items[idx]` survive. - `native_tts.rs` - The **processor voice** (issue #29) and the **native-only voices**: Kokoro runs natively through sherpa-onnx for machines whose WebView cannot run it on the graphics card (no WebGPU, which is most Linux, or a driver that garbles it), and Kitten, Pocket TTS and Supertonic only ever run here. It is CPU-only on purpose: sherpa-onnx ships GPU builds only for NVIDIA CUDA (~0.5 GB, plus the CUDA and cuDNN runtimes), and these models are small enough that a batch-of-one GPU run gains little. Inside the WebView those machines got single-threaded WebAssembly, about 10 s per reply. Natively, all cores measured RTF 0.20 at 8 threads on a Ryzen 7700X, with the first sentence in about 0.3 s. **Nothing ships in the installer.** The engine (onnxruntime plus the sherpa C API, 7–12 MB per platform, pinned to 1.13.8 with a SHA-256 per platform) downloads with the first voice pack into `models/tts-runtime/sherpa-onnx-<ver>/` and is loaded with `libloading` at first use. It is deleted when the last pack goes, and `init` removes other versions at launch. The packs are ordinary catalog models (`EngineType::NativeTts`: `kokoro-82m-native` 350 MB, Kitten `kitten-nano-0.8` / `kitten-micro-0.8` / `kitten-mini-0.8` at 64 / 44 / 68 MB, `pocket-tts` 168 MB plus its voices, `supertonic-3-int8` 129 MB), so download, resume, cancel and delete are the model manager's own code. The native-only engines are `NATIVE_ENGINES` (`kitten`, `pocket`, `supertonic`); Kitten's size is that engine's `assistant_tts_model` (a catalog id, empty = nano, which is what every earlier version installed). **Pocket TTS has no built-in speakers**: each voice is cloned from a short reference recording, recording quality included, so its 14 voices are WAVs fetched after the archive (`install_voice_clips`) from `kyutai/tts-voices` pinned to one commit, each checked against a SHA-256 in `POCKET_VOICES`. Which recordings ship was decided by scoring every one (UTMOS naturalness plus speaker similarity): Kyutai's voice-donation clips (Marius, Javert) are phone recordings that rendered badly or ran away, and its default Alba is a 126 Hz recording that sounds mislabelled as a woman's voice, so those and the two lowest scorers are left out, as are the two non-commercial presets. Three Pocket settings are load-bearing, all measured. **fp32, not int8**: int8 scored lower and misread half again as many words (and k2-fsa/sherpa-onnx#3172 says the same by ear). **One call per sentence with a frame ceiling** (`pocket_pieces`, `pocket_max_frames`): Pocket's end-of-speech signal often never fires on short text, and the engine then generates to its 500-frame limit, 40 s of breathing for "Sure."; Kyutai's own fix (padding with spaces) does nothing through sherpa-onnx, which drops them. **Pauses kept whole** (`silence_scale` 1.0, not the 0.2 the other voices use). Temperature 0.3 and 1 flow step are Kyutai's defaults. Pocket is still weak on one- and two-word prompts even with the ceiling, and it follows its reference clip's pace, so it has no speed control. `is_downloaded` also requires the runtime to be present, and every file the pack's engine opens (`VoicePack::required_files`, which includes Pocket's clips). **One engine at a time**, dropped after `IDLE_UNLOAD` (180 s) or when the voice is switched away (Kokoro ~400 MB resident, Kitten ~80 MB). **Routing is Rust's call** (`route` → `VoiceRoute::{Webview, Native, Remote}`), but only a WebView can see the GPU, so the WebView reports it (`assistant_report_webgpu`) from three places: a cheap adapter probe (`useLocalVoiceStatus`), a WebGPU init failure, and the broken-audio check on the first two WebGPU clips (`audioLooksBroken` in `src/assistant/localVoice.ts`, calibrated on real speech: ZCR 0.05–0.14, RMS 0.06–0.13). A GPU that corrupts Kokoro throws nothing, so the samples are the only evidence. A failed check mutes the reply, persists `speakoflow.kokoro.gpuBroken` for Automatic, and moves the next reply to the processor. `assistant_tts_kokoro_device` is `auto` / `gpu` / `cpu`, and the old `q8-cpu` precision migrates to `cpu`. **Automatic never makes the voice worse**: it only goes native when WebGPU is unusable _and_ the pack is ready, otherwise Kokoro stays in the WebView. A library that refuses to load (macOS library validation on an ad-hoc-signed app is the expected case) latches `LOAD_FAILED` for the session, so every pack reads as not ready and Kokoro falls back rather than failing each reply. `local-voice-status-changed` tells the windows. Two FFI details matter. Windows loads with `LOAD_WITH_ALTERED_SEARCH_PATH`, because System32 ships an unrelated `onnxruntime.dll` (1.17) that a plain load binds to. Paths go through 8.3 short names, because the C API opens narrow strings in the ANSI code page. The `#[repr(C)]` structs mirror `c-api.h` 1.13.8 exactly, including model families the app never uses, since a missing field shifts every later one. Each model's own speed 1.0 is a different pace, so every pack carries a `pace` that maps the app's 1x to a normal speaking rate (Kitten nano 1.6, micro 1.5, mini 1.3, Supertonic 1.2, measured in words per minute against the same sentences). Kokoro is configured `lang=en-us` with no lexicon, which loads faster and uses 42 MB less; British voices pass `{"lang":"en"}`, because espeak rejects `en-gb`. The int8 variants were measured and rejected: ConvInteger makes Kokoro int8 slower than fp32 (RTF ~1.0). sherpa 1.13 statically includes eSpeak NG (GPL-3.0). It is downloaded at run time from upstream, never bundled or redistributed by us.
- `web_search.rs` - Optional web search, fully model-decided: the assistant calls a `web_search` tool and `run_tool_search` turns the tool args into a one-query `SearchPlan` fed to `search_with_plan` (parallel snippet search + local rerank) — there is no separate planner or keyword heuristic. Six snippet-only backends (Serper default, Brave, Tavily, Exa, SerpAPI, TinyFish); a `WEB_SEARCH_CAPABILITY_NOTE` is folded into the system prompt when search is enabled. - `voice_conversation.rs` - Hands-free spoken sessions (the assistant panel's "call" mode). Session/turn tickets make late STT results and synthesized audio harmless after a barge-in, mute, or End. **A superseded utterance's transcript is carried forward, never dropped** (`carry` / `with_carried`): the frontend VAD ends an utterance after `TURN_PAUSE_MS` (450–1100 ms) of silence and starts a turn, so one thought spoken with a pause in it — "my name is Abhishek, <pause> can you help me with this?" — is two utterances, and resuming speech supersedes the first one's turn. Transcription almost always loses that race (the frontend interrupts ~160 ms into the resumed speech, while STT is still running, and on a cloud engine or a cold local model it is not close), so returning early on `!is_current` silently threw the first fragment away and the assistant answered only the words after the pause. Carried speech is scoped to the live session, expires after `CARRY_FORWARD_WINDOW` (so a fragment abandoned at mute does not reappear in front of the next question) and is capped at `MAX_CARRIED_CHARS`. A turn that starts and is _then_ cancelled needs none of this — its user message is already in history, and `llm_client::enforce_alternating_roles` merges the consecutive user messages at send time. `end_session` is also where a spoken conversation reaches memory: closing the panel during a call defers distillation (`assistant::distill_conversation_if_ended`) to the hang-up, because a live call is not an ended conversation. **Closing the panel hangs up, and hanging up closes the panel.** Hiding used to leave the microphone open, every utterance still answered and spoken aloud from a window that was no longer visible, while the X read as "hang up". `hide_assistant_panel` therefore ends the session (so the hotkey and tray paths agree with the button). The other direction was the mirror-image bug: ending the session left the window up, so the panel re-rendered as the quick-ask card and End looked like it had opened a second, different assistant. So **every** hang-up goes through `hide_assistant_panel` rather than `voice_conversation::end`: the End button and the in-webview Escape (`onHangUp`, threaded into `useVoiceConversation` because the hook cannot reach the window), the `assistant_call` shortcut's second press, and the global Esc. Esc is the one conditional case — mid-reply it stops the reply and keeps the call, and only hangs up when the assistant is idle, because hanging up mid-answer discards the thing the user is listening to. `voice_conversation::end` on its own is still what the _assistant_ shortcut calls, which must take the microphone back and then show the quick-ask card. **Dictation does not hang up a call; it holds it.** It used to, because both want the microphone, and the hang-up threw the call's whole conversation away to type one sentence somewhere else. Now `DictationTracker` (`dictation_started` in `TranscribeAction::start`, before the mic opens; `dictation_recorded` the moment `stop_recording` returns; `DictationFlight` ending the pipeline on every exit path; `dictation_cancelled` on a cancelled or failed start) emits `assistant-conversation-dictation` and the call's VAD pauses until recording ends, exactly as the mute button pauses it — a reply already on its way keeps playing, and the two switches are independent (`syncMic` in `useVoiceConversation` serializes both onto the VAD, so ending a dictation never unmutes a muted call). The tracker has three stages because the microphone and Esc are released at different times: the call listens again as soon as the audio is in, but Esc belongs to the dictation until it has pasted (`esc_hangs_up`), and a cancel during a dictation leaves the call's reply, voice and state alone (`cancel_spares_call` in `utils::cancel_current_operation`). Generations stop a pipeline released early by the coordinator's processing cap from ending a newer dictation's hold. A call started mid-dictation begins held (`call_may_start`; the webview asks `assistant_conversation_dictation_active`, since it missed the event), and while a call is up the bottom-docked recording overlay rises to `assistant::CALL_STACK_CLEARANCE` so it never covers the call bar. And because Rust considers a call active from the moment it issues the ticket — before that id reaches the webview — `assistant-conversation-ended` is honoured by a frontend session that has no id yet (`closedSessions` distinguishes that from a previous session's late event); requiring the ids to match left the VAD holding the microphone for a call the backend had already torn down. The pause the VAD waits for is fixed at `TURN_PAUSE_MS.natural` (700 ms): the panel passes `pace: null`. The "time to finish speaking" dial that used to set it (`assistant_conversation_pace`, still persisted and still accepted by `useVoiceConversation`) was removed from the call's options because it asked people to tune a number they cannot reason about, and a stored value must not keep applying with no control left to change it
- `transcription_coordinator.rs` - Single-threaded recording state machine; also owns `recording_mode`, which maps a shortcut's Hold or Tap (`settings::holds_to_record`) onto `Hold` or `Lock`, and `Abort`, which throws away a recording whose press the hotkey engine withdrew. A held dictation turns `Lock` without stopping (`keep_listening`) on the hands-free key (`Command::HandsFree`, never debounced, since pressed right after the dictation keys it can land inside their press debounce); to anything else, the ask or a dictation already hands-free, the key does nothing (`keeps_listening`). `claim_processing` lends its idle stage to a dictation being recovered, so a hotkey pressed during an Undo is "busy" instead of a second dictation racing it for the overlay and the paste. **A hands-free dictation can end itself on silence** (`dictation_silence_stop_secs`, Off by default, Settings → Shortcuts). `silence_timeout_for` is the one place that decides which recordings qualify: the dictation and dictation-plus-cleanup shortcuts (CLI toggles included) in `Lock` mode, which with Hold to talk means a dictation turned hands-free (`hands_free.rs`); never a recording still held, the assistant, a call or a meeting. A `SilenceWatch` reads `AudioRecordingManager::speech_activity`, which is lock-free (the recorder's own lock is held for seconds while a microphone opens or drains) and counted in samples on the audio's own clock, so a slow-to-wake microphone never makes the user seem quieter than they were. It is reset in `AudioRecorder::start`, before `Start` is queued, so a check can never see the previous recording's silence. The watch ends the recording through the same `stop` a second tap uses, and has its own deadline next to the stage's: it re-arms on every check, and folding it into the stage deadline would push the 30-minute cap out. In the last ~2 s it emits `recording-silence-countdown`, and the pill draws a hairline that runs out, removed the moment speech resumes. Nothing announces it to a screen reader, because an announcement would be spoken into the microphone and count as speech. A recording in which nothing was said needs no special case: its VAD-filtered audio is empty, and the pipeline already ends an empty recording without transcribing silence
- `hands_free.rs` - **Hands-free dictation**: a dictation that keeps listening after its keys are let go, until they are pressed again, ✓ on the pill, or Esc / ✕. A state a dictation can be in, not a third recording mode: with Tap to toggle every dictation is hands-free; with Hold, the hands-free key (`settings::HANDS_FREE_BINDING_ID`, Space by default, removable), pressed while the dictation keys are held, turns the running one hands-free. Space is Wispr Flow's hands-free key (Ctrl+Win+Space, Fn+Space) on top of keys that are already Wispr's. It is one key, stored as a binding but never registered on its own (`shortcut::register_shortcut` refuses it, since alone it would take Space from every app): `keys_for` puts it on top of each dictation shortcut's live keys, so it follows them when they change, and `change_binding` keeps only the main key of whatever was recorded (`main_key`), so recording it while holding the dictation keys works. It exists only for dictation keys that are modifiers alone, only on SpeakoFlow Keys, only while dictation is held to talk (with Tap, Ctrl+Win+Space stays Windows' own), and it steps aside when another live shortcut is on those keys (`keys_for` reads what is registered, not the stored settings, which lag a binding being changed and include shortcuts that are switched off). Two engine details carry it. It is registered as a continuation (`HotkeyManager::register_continuation`), because to the engine any key typed onto a fresh modifier-only press is the start of another shortcut and would withdraw the dictation; and blocking it is what keeps Windows from seeing Win+Ctrl+Space, which the hook used to replay as "switch to the previous input method". Registering it only while a dictation is held, the way Cancel is, was considered and rejected: a key pressed together with the dictation keys can arrive before such a registration does, and the dictation is then withdrawn as the start of another shortcut. `HandyKeysState::sync_hands_free_keys` re-derives both dictation shortcuts' hotkeys after anything is registered or released and after either mode changes, after launch's whole registration rather than during it, so the order bindings register in never decides a conflict. `src/lib/handsFree.ts` mirrors the rule for Settings and Home. A dictation shortcut with a main key of its own (Linux's Ctrl+Space, an F-key) has no hands-free key; Tap to toggle is its hands-free. **How it is shown** decides whether anyone finds it, and two versions got it wrong. "Hands-free mode" with "+ Space" read as a setting to switch on and half a shortcut; the next one drew the whole combination (Ctrl + Win + Space) behind a verb on every row ("Hold", "Tap", "Press"), which read as three keys to press at once and turned Home into a wall of words. Now every shortcut row is a name, an (i) and its keys, nothing else, and the (i) is where the gesture is explained (`components/settings/shortcutInfo.ts`, shared by Home and Settings so the two cannot disagree, and it follows Hold to talk). The one exception is the hands-free row, **Hands-free**, whose key is pressed while dictating, so it reads "While dictating, press [Space]". Hold to talk is a plain switch row under its shortcut in Settings → Shortcuts (`PushToTalk`), for dictation and for the ask. Where there can be no key (Linux, the other engine) Settings says to turn Hold to talk off, and Home shows a one-line hint under Dictate with **Turn off** and an X that closes it for good (`speakoflow.home.handsFreeHintClosed`). And the pill teaches it: a held dictation's show carries `hands_free_key` (only while one is really registered, `handy_keys::hands_free_key`) and `finish_keys`, and for the first few held dictations (`overlay/handsFreeHint.ts`: three, or until one goes hands-free) a lock and the key's keycap take the waveform's slot after ~0.9 s, so the pill never resizes. The hands-free card's header reads "Recording", exactly like a held one: "Hands-free · Ctrl + Win to finish" was read on every dictation by people who had learned it once, and the ring already says it, while the finish keys stay on ✓'s tooltip and in the card's `aria-label`.
- `dictation_recovery.rs` - **Undo for a dismissed or failed dictation.** Cancelling used to be final: Esc mid-recording threw the audio away (`AudioRecordingManager::cancel_recording` discarded it), and a cancel or a failure later in the pipeline dropped whatever was already done. Now each leaves an `Offer` — what is left to do (`Remaining::Transcribe` / `Deliver` / `Paste`) plus its History row — and the pill turns into a quiet "Dismissed · Undo" or "Transcription failed · Try again" for 2.5 seconds (`overlay::show_recovery_overlay`, held open by hover). The offer is keyed by the overlay epoch that showed it, so a click on a pill that has since been replaced can never act on another dictation, and it is withdrawn the moment anything else takes the overlay. Taking it (`recover_dictation` → `actions::start_recovery`) resumes the dictation where it stopped, through the **same** `deliver_transcription` the live pipeline uses, so a recovered dictation pastes exactly what the original would have. Every dismissed dictation also keeps a History row with `dismissed = 1`, which counts nothing toward usage until it is recovered (`counted_words`), and History's Recover (`recover_history_entry`) finishes it without pasting. Three things are deliberately **not** offered: under half a second of speech (`worth_keeping` — a stray hotkey press cancelled on purpose), anything headed for the assistant or an in-app field (recovering pastes, the wrong destination for both), and any platform where a clickable overlay could take keyboard focus from the paste target (`live_card_takes_pointer`, so X11 without layer shell keeps the old hide)
- `smart_spacing/` - **Smart spacing** (`settings.smart_spacing`, on by default since 2.1.0, for an update as much as a new install; `smart_spacing_fix_case` and `smart_spacing_join_sentences` refine it). Two dictations into one field used to run together ("hello" + "there" pasted "hellothere"), because a paste knows nothing about the field. With it on, the field is read twice per dictation, in the background, while the user talks: at recording start (`begin`, right after `remember_paste_target`, before any window of ours is in front) and at stop (`refresh`, alongside the transcription). `paste_final` calls `prepare` before taking the main thread; it waits at most `PASTE_WAIT` (100 ms) for a read still in flight and otherwise uses the earlier one, because reading at paste time is what made OpenWhispr drop the same feature (an Accessibility round trip felt on every paste). The newest reading that learned something wins; an `Unknown` never replaces an informative one. **The readers** return a `reading::Reading` (`Text { before, after, selected }`, `Empty`, `Unknown`, `Terminal`, `Secret`) and each runs on its own dedicated thread behind a `BUSY` flag, so a read stuck in a hung app is skipped rather than queued behind: `windows.rs` (UI Automation, a separate thread from autolearn's, `CUIAutomation8` with 200 ms connection and transaction timeouts, the insertion point is the start of the single selection range with `GetCaretRange` only when active, both sides clamped to the document range, focus re-checked after the read, password fields and terminals never read; the window is named before the worker is asked, so a read that is skipped or times out still feeds the last-paste memory instead of wiping it, and a quick `Unknown` is read once more 120 ms later, because Chrome switches its accessibility on at the first request and answers that one with nothing: measured on Chrome 155, nothing in 17 ms, then the text 100 ms later), `macos.rs` (AX on a worker thread with 0.2 s messaging timeouts, `AXStringForRange` on a small UTF-16 window, `AXManualAccessibility` leased for Chromium and Electron apps and switched back off after a minute, **never** `AXEnhancedUserInterface`, which leaves an app in screen-reader mode for life, secure input and `AXSecureTextField` never read), `linux.rs` (AT-SPI over zbus on its own current-thread tokio runtime, focus followed from `object:state-changed:focused` events with a bounded search before the first one arrives, Chromium paragraph placeholders U+FFFC followed through Hypertext into the paragraph holding the caret; tested end to end against GTK3 fields under Xvfb). Chromium, Electron and Qt on Linux expose text only when the desktop accessibility setting is on, and SpeakoFlow deliberately does not switch it on. **The rules** (`rules.rs`, pure, table-tested from the case lists of Talon, OpenSuperWhisper, TypeWhisper, xhisper and voxtype) shape only the inserted text: a leading space unless the caret follows whitespace, an opener, a glue mark (`@ # / \ - _`) or an elision, or the dictation starts with punctuation; a trailing space **only** when a word follows the caret (an unconditional trailing space is the bug TypeWhisper users filed and it removed); no space next to a script written without spaces (Han, kana, Thai, Lao, Khmer, Myanmar, Tibetan and others, but not Hangul); lowercase the first word only mid-sentence and never "I", acronyms, mixed case, dictionary words or names seen capitalised around the caret, and never for German or Turkish; drop the dictation's own final mark when the text after the caret continues the sentence. One rule touches existing text: a period SpeakoFlow itself pasted moments ago after a word a sentence cannot end on ("I went to the.") is removed with one Backspace (`clipboard::send_backspace`) when the next dictation continues it, only after the reader confirmed the field still ends with exactly that paste, and only while the window in front is the one the reading came from (`still_aimed_at_reading`), since the paste respects an app switch made during the transcription. **A Chromium address bar trims pasted text** (`OmniboxViewViews` in Chrome, Edge, Brave and the rest: Chromium collapses and trims the whitespace of anything pasted there), so the leading space went in with the paste and came out without it, and dictations ran together ("feature.Don't") although the field read and the rule both said space; the Windows reader flags that control (`Snapshot::trims_pasted_spaces`) and the space is typed first (`clipboard::send_space`). **When the field cannot be read**, the last-paste memory (`record_paste`, the tail of SpeakoFlow's own paste per window/app, 45 s) adds the leading space a continuation needs and nothing else; with neither, the dictation pastes exactly as before and `append_trailing_space` applies as it always did. An auto-submitted paste clears the memory, the clipboard copy keeps the dictation without the fitted spaces, and the log carries the focused control's type, framework and class, why a read learned nothing, counts and the kind of the last character before the caret, never field text. `smart_spacing::windows::live_tests` (ignored) reads whatever field is in front and prints it, for checking an app by hand
- `autolearn/` - **"Learn words I correct"** (Windows only; macOS/Linux report `supported: false` and the UI says so). After a successful paste, `watch.rs` reads the one focused control over UI Automation for a minute and `detect.rs` turns a one-word fix into a `learned_words` entry, which `recognition_words` feeds to every engine. The first version learned nothing for anyone: it read the field once, milliseconds after a synthetic Ctrl+V the target had not processed yet, and it trusted `ValuePattern`, which on a Chromium web document is the page **URL**. So every dictation logged "the focused control does not contain the transcript". The watcher now retries acquisition for `ACQUIRE_FOR` (4 s), reads both Value and Text patterns and watches whichever actually holds the transcript, and only judges a reading once it is unchanged across two polls (`Settle`), so a word caught half-typed is never learned. When acquisition fails, the log names the control type, class, framework and pattern lengths, never the text
- `actions.rs` - Post-recording output pipeline: pastes the transcript and runs the optional, experimental **AI Correction** post-processing pass (`post_process_transcription`, `resolve_post_process_provider_and_model`, `prewarm_builtin_llm`) — cleanup plus a tone directive (`PostProcessTone::directive()`) in a single LLM call, wrapped in `tokio::time::timeout(post_process_timeout_secs)` and falling back to the raw transcription on timeout or failure. Cleanup runs on its **own** llama.cpp process (`CleanupLlm`, port 11436) which `prewarm_builtin_llm` starts _and warms with a real prefill_ at recording start; `prewarm_assistant_llm` does the same for the assistant's engine. Output is validated by `validate_cleaned_output` → `sanitize_post_process_output` (strips fences, `<transcript>` tags, leaked `<think>` blocks) plus `is_implausibly_long`, which rejects the classic small-model failure of narrating a plan instead of cleaning the text. `validate_cleaned_output_against_prompt` adds the checks that need the system prompt: `prompt_echo` rejects an answer that repeats the prompt's worked examples or instructions (feedback #8: Gemma 4 E2B answered "Thank you." with both Readable examples, short enough to pass the length check), and a bare gpt-oss channel name (`final`) or punctuation-only answer is rejected too. The structured-output field is `cleaned_text`, **never `transcription`**: named after the input, gpt-oss-120b (Azure) and Gemma 4 E2B copied the raw transcript into it, so cleanup "succeeded" while changing nothing. On the built-in engine a general model now gets a real `system` message (`keeps_system_role`); only a template that refuses one is folded, behind `FOLDED_TRANSCRIPT_BOUNDARY`, because the old unbounded fold glued the transcript onto the examples. `post_process_thinking` / `assistant_thinking` (`settings::ThinkingLevel`, default `Off` = the old fast path) send an explicit `reasoning_effort` (OpenRouter: `reasoning.effort`); Anthropic, Apple Intelligence and the built-in engine take no request-level control and the UI says so. **A short dictation can skip cleanup** (`post_process_skip_short` + `post_process_min_words`, on by default at 15 words; issue #63): `skips_short_cleanup` decides on the transcript in `deliver_transcription`, and only for cleanup that rides on the dictation shortcut. The dedicated cleanup shortcut is a request for cleanup, so it always cleans; that is carried as `DictationContext::explicit_cleanup` rather than inferred from `flow_eligible`. Words come from `audio_toolkit::count_words`, which estimates Chinese, Japanese and Thai-family text from the character count. A skipped dictation's row still records `post_process_requested = true`: the column says what was asked for, not what ran, so History's Recover/Retry (`rerun_runs_cleanup`) judge the rule again on the transcript they produce, and a retranscription that comes back long is cleaned. A row does not store which shortcut asked for cleanup, so a rerun uses `cleanup_on_dictation` as the stand-in (the dedicated shortcut is unregistered while cleanup rides on dictation). Words in the Thai-family scripts count their combining marks: Thai tone marks are not `is_alphanumeric`, and dropping them read a five-word Thai sentence as four. **A cleanup cut off at the output limit is never pasted** (`cleanup_content` → `ChatCompletionError::Truncated` → `PostProcessFailureKind::Truncated`, Handy #2257): it reads as finished up to where it stops and drops the rest of the dictation, so the transcript is pasted instead. `llm_client::is_truncation` reads `finish_reason` as `length`, `max_tokens` or `max_output_tokens`; a missing one reads as finished, and a cut-off answer with no visible text stays an empty answer, which is what sends a reasoning model to the uncapped retry. The assistant still shows a long answer that was cut off. A recording that yields no audio calls `maybe_unload_immediately` itself (Handy #2106), because that exit never reaches `transcribe`, which is what unloads a model set to "Immediately". On Linux with glibc the end of every pipeline calls `malloc_trim(0)` (`trim_freed_memory`, Handy #1846): glibc kept the freed audio buffers, so resident memory grew with each dictation
- `overlay.rs` - Recording overlay window (platform-specific). Two properties matter more than the drawing. **It must never take keyboard focus.** The window is deliberately larger than the visible pill (the pill hugs its content and floats inside a transparent frame), so most of it was invisible padding that sat in front of the user's app, swallowed clicks, and — because a click _activated_ it — moved keyboard focus off the field being dictated into, after which the synthetic Ctrl+V pasted the transcript into the overlay's own webview and it vanished. The compact pill never takes the pointer. The live card takes it from the first word wherever the window cannot take keyboard focus, which `live_card_takes_pointer` decides per platform: Windows sets `WS_EX_NOACTIVATE`, macOS uses a panel that never becomes key, and a GTK layer surface is created with `KeyboardMode::None`. Scrolling back through live text, selecting a phrase, and the copy button are why the card exists, and a click-through card drew all three while letting none of them work. `ShowOverlayPayload.interactive` tells the webview which case it is in, so it never offers a control the window would pass straight to the app underneath. A click can focus an ordinary X11 window, so there the card stays click-through until `finish_recording_overlay` hands the pointer back after the paste. On Windows it is also `set_focusable(false)` (`WS_EX_NOACTIVATE`) so a click that does land cannot take the foreground at all. A hands-free dictation is the one recording that takes the pointer, for its ✕ (`cancel_operation`, so it leaves the Undo offer Esc does) and ✓ (`commit_recording`); a held one never does, since its keys are under the user's fingers. `HANDS_FREE` is read by the recording's own show rather than only announced, because that show can come after the turn (`shortcut::chord` holds it back), and `enter_hands_free` redraws one already on screen. **And it must stay on top for a whole recording, not just the moment it appears.** `force_overlay_topmost` ran once per show, but `WS_EX_TOPMOST` is a position another process can take; `start_overlay_topmost_guard` re-asserts it on a 700 ms tick while the overlay is up and `warn!`s once per displacement naming whether topmost or visibility was lost — which is what turns "the dictation window hides randomly" into a log line. The guard's generation counter is retired by `hide_recording_overlay` _before_ the window goes down, so a tick already queued on the main thread cannot resurrect a deliberately hidden overlay. `get_monitor_with_cursor` hit-tests the cursor against monitor bounds in physical pixels first and logical points second, rather than pre-scaling the bounds: the cursor is physical on Windows/X11 and logical on macOS, and scaling only one side made every monitor look smaller than it is, so on a scaled multi-monitor desktop the overlay fell back to the primary display. **A dictation that ends before its model has loaded says "Loading model…"** (`loading`, Handy #2227), not "Transcribing…", whose forward-only fill parked near its end for the whole load and taught the fill's history a load as transcription time. `show_transcribing_overlay` picks the state, `load_change` maps a load starting or ending onto what is shown, and `watch_model_load` polls `TranscriptionManager::is_model_loading` together with the `model-state-changed` events, because each is a moment apart from the other and either alone can be stale. A recording still running gets `overlay-model-loading` instead, and the card only mentions a load that lasts ~2 s
- `audio_feedback.rs` - Feedback-sound playback with selectable themes (`SoundTheme`: Default/Marimba/Pop/Click/Custom, resolved per start/stop from bundled resources), `play_test_sound` for in-settings previews, and `play_reminder_sound` — the one cue **not** gated on `audio_feedback`, because that switch means "don't beep when I start dictating" and a reminder whose whole job is to reach someone looking elsewhere must not be silenced by it. It reuses the theme-independent `popo_lock.wav` that belonged to the removed mid-recording lock gesture and had been unreachable since (`SoundType::Lock` → `SoundType::Reminder`)
- `signal_handle.rs` - `send_transcription_input()` reusable function
- `speech_readiness.rs` - The gate every voice shortcut passes before it records (`TranscribeAction` / `AssistantAction` / `AssistantCallAction`). First-run setup starts the speech model downloading and then tours the app, so the first press often comes before the model has landed; the press used to open a recording that could only fail. `resolve` is a pure function over a snapshot (cloud configured, the selection, the catalog): a downloaded selection or a complete cloud setup is ready; a speech model downloading refuses the press and shows the overlay's `downloading` pill (`overlay::show_speech_download_overlay`), which follows that model's `model-download-progress`; nothing on disk and nothing coming shows the `noSpeechModel` notice. A download in flight wins over a stale model on disk, because the setup queue selects a model only once its file lands. **A retired selection is `NeedsUpdate`**, checked before every other rule: its files on disk do not make it runnable, and the stale-selection rule ("another model is downloaded, so the press is fine") must not apply, since the pipeline would load the retired selection and fail. Its new version (or any other speech model) downloading reads as `Downloading`; otherwise the press is refused with the overlay's `update` pill naming the model, and `open_update_prompt` brings the main window forward on the Models page's speech tab (`SPEECH_UPDATE_EVENT`, `shell/speechUpdate.ts`). Meetings and History's retranscribe call `retired_selection_message` instead, which ignores a download in flight (they transcribe now, not after it) and returns the loader's own sentence (`retired_engine_message`), so a meeting, a retranscription and a failed load say one thing. Hanging up a call is never refused
- `updates.rs` - What the updater plugin does not decide: whether **this** install can replace itself (`resolve_install_mode` → `UpdateInstallMode`: `InApp` / `Download` / `Portable` / `PackageManager`), and the manual fallback (`download_update_installer`, which saves the right full installer to Downloads from the `speakoflow.downloads` block of `latest.json`, and `open_update_installer`). The plugin would happily do the wrong thing on Linux: an install with no bundle type (from source, AUR) falls through to its AppImage path and overwrites the running binary, and a `.deb` is installed with `dpkg -i` even on Arch. So in-place install is offered only for NSIS/MSI, macOS, a running AppImage (`APPIMAGE` set), and a `.deb` on a Debian-family system with a way to ask for the password. Downloads are confined to this repo's `releases/download/` URLs and plain `SpeakoFlow*` file names. **A Windows in-app install skips `RunEvent::Exit`**: the plugin starts the installer and calls `std::process::exit` itself, so `prepare_update_install` (which the frontend calls between `download()` and `install()`) runs `lib.rs::release_before_exit` first on Windows, the same meeting stop and engine teardown every ordinary quit gets. macOS and Linux need nothing extra, because their relaunch goes through `request_restart`, which does fire `RunEvent::Exit`
- `feedback.rs` - In-app feedback. `send_feedback` posts to the Cloudflare Worker in `feedback-worker/` (`FEEDBACK_ENDPOINT`), which files an issue in the private `AbhishekBarali/speakoflow-feedback` repo. Sent from Rust, not the webview, so there is no CORS surface; the Worker answers no preflight. What is sent is exactly what the dialog shows: message, email only if typed, up to three screenshots (pasted or picked, shrunk in `components/feedback/screenshots.ts` to ≤1920 px WebP/JPEG around 100–400 KB, committed by the Worker under `attachments/YYYY-MM/` and embedded in the issue), and the system line only if its box is ticked. No logs, no transcripts. The Worker's credential needs Contents: write as well as Issues for screenshots; without it the report still arrives and the issue says its images were not stored
- `utils.rs` - Platform detection helpers

### Frontend Structure (src/)

The app ships four Vite entry points: the main settings window (`App.tsx`), the
floating assistant panel (`assistant/`), the recording overlay (`overlay/`), and
the reminder popup (`reminder/`).

- `App.tsx` - Main window: renders the custom `TitleBar`, the sidebar, the active page, and the Settings dialog, all inside `shell/navigation.tsx`'s `NavigationProvider` (also drives the onboarding flow). The old footer is gone; its three jobs moved: the speech-model status line and download indicator live at the bottom of the sidebar, update checks run from `UpdateChecker` (renders nothing; results show in the sidebar's `UpdatePill` and Settings → About), and switching to a freshly downloaded speech model is `useAutoSelectDownloadedModel` (`shell/useSttStatus.ts`)
- `components/` - React UI components:
  - `TitleBar.tsx` - Custom window chrome (brand wordmark + minimize/close). The native chrome is disabled in `lib.rs`, so this bar also acts as the drag region; macOS keeps native traffic lights via an overlay title bar
  - `Sidebar.tsx` - Primary navigation. Pages are things you do: Home, History, Assistant, Meetings, AI cleanup, Dictionary, then Models below a rule; the gear at the bottom opens Settings. `useNavigation()` (`shell/navigation.tsx`) is how any page links to another (`navigate`, `openModelSlot("cleanup")`, `openSettings("shortcuts")`)
  - `pages/` - One component per sidebar page. `models/` is organised by the **job** a model does (speech to text, AI cleanup, assistant, voice), not by file type. The speech catalog (`settings/models/ModelsSettings.tsx`) opens on **Recommended**, not on all 69 models: the user's own models, then `speechCatalog.ts::recommendedModels` for the language picked beside it (the catalog's `recommended` five, the ones Handy recommends and setup offers; for one language the ones that hear it, topped up to three by accuracy and speed together), and **All models** is one click away with search and the streaming and translate filters, which only the full list needs. Accuracy and speed are two thin bars in a column of their own (`ModelRow.tsx::ScoreBars`), so they line up down the list; five dots each on every row piled up into noise; `shell/useModelSlots.ts` is the single derivation of "what is powering each job right now" (including cleanup borrowing the assistant's model via the backend readiness resolver), shared by Home, Models, AI cleanup, Assistant, and Meetings so they cannot disagree
  - `settings-dialog/` - The Settings window (`tabs.tsx`: General, Shortcuts, Audio, Dictation, Privacy & data, Advanced, About, Debug). App-wide preferences only; features and models live on their pages
  - `settings/` - The building blocks the pages and dialog compose (rows, groups, catalogs, `AssistantSettings` with a `sections` prop so each page renders only its part). The `memory` and `characters`/Profiles screens live under `assistant/` (`MemorySettings.tsx`, `CharactersSettings.tsx`)
  - `model-selector/` - Model management interface
  - `onboarding/` - First-run setup: welcome, the permission check (`AccessibilityOnboarding.tsx`), then two screens under one step list (`OnboardingFrame.tsx`). **Every screen is drawn with the main window's own parts** — the inset `bg-canvas` sheet, `font-display` titles, `Button`, `Tabs`, `Keycaps`, `ShortcutInput`, settings-group cards — and `onboarding.css` only holds motion and the tour's stage geometry; the previous version had its own type scale and components and read as a different product. **Onboarding shows, it does not explain**: a headline, the keys, and a real surface moving; the previous two versions had a paragraph and a footnote on every screen, and nobody read them. **Set up** (`SetupStep.tsx`) is a radio list of five speech models (`SETUP_SPEECH_OPTIONS`) and only those five: Parakeet 0.6B, Nemotron 3.5, Canary 180M Flash, Cohere Transcribe, Whisper Medium. Each card shows one plain name with the languages it hears beside it (`English` / `28 languages`, names on hover), one sentence of what it is for (`onboarding.speech.about.*`), and its size or that it is installed. That is deliberately all: a third line of capability chips and accuracy/speed dots made a five-way first-run choice read like a spec sheet, and the sentences already state each model's trade-off; the full facts are on the Models page. It used to append every other installed speech model too, and the catalog's near-namesakes (an ONNX and a GGUF Canary 180M Flash, two Whisper Mediums) made the list read as the same model offered twice; the one exception now is the model a replaying user already dictates with, shown marked "In use" so Continue keeps it. It downloads only that model. **Tour** (`TourStep.tsx`, `tourScenes.tsx`) is three looping scenes — dictation, assistant, call — each rendering the real surface (the overlay's card markup, `QuickAsk` itself, the call bar's `CallBar.css` classes with `VoiceOrb`) beside a two-line headline and the keys; the assistant tab lists example chips (Translate / Write a reply / Explain / …anything). It downloads and enables nothing. **Start** (`FinishStep.tsx`) used to follow the tour, a download screen that became a try-it box, and it is gone: the speech model is rarely downloaded by the time the tour ends, so it was mostly a progress bar to wait on. The tour's last button opens the app; the download carries on behind it (sidebar), and a dictation pressed before it lands gets the overlay's `downloading` pill. **The tour's copy column holds still** — the numbered steps, the keycaps and the assistant's example chips used to light up in turn with the preview, and that second animation beside the first was distracting. The stage grows with the window (`.ob-stage`, up to 46rem) and the scenes scale up with it (`--ob-scale-h` / `--ob-scale-w` container queries), so a big window shows a bigger scene rather than more empty desktop. The permission step renders an empty sheet while it checks and when nothing is needed, so it passes through without a flash. Downloads are `setupQueue.ts`, a module-level store that runs them **one at a time** and only points a job at a model once its file is on disk; it outlives the screens. Completion is a `localStorage` flag (`completion.ts`), and it is the **only** gate: every install sees onboarding once, including one that already has a speech model or dictates in the cloud (setup shows an installed model as installed, so Continue keeps it, and "Set up later" changes nothing). There is deliberately no "returning user" detection any more; bumping the flag's `VERSION` shows the flow to everyone again, which is how a large redesign reaches existing installs. Because shortcuts are only registered once onboarding is done, an un-onboarded launch reveals the main window even when started hidden, so the hotkeys are never dead behind an invisible window. The tour has no Skip: three scenes, Next only. There is no in-app way to replay onboarding (a "Show onboarding again" row in Settings → General existed for testing and was removed); in dev builds `FORCE_ONBOARDING` in `App.tsx` shows it on every launch, and the preview's `?onboarding=` parameter opens it at any step. `ModelCard.tsx` is only kept for the Models settings list
  - `ui/` - Shared primitives; `ui/tones.ts` defines the semantic icon-tile / pill color tones (`SettingTone`, `TONE_TILE`, `TONE_PILL`) used by the iOS-style setting rows. **Feature banners** (`ui/Hero.tsx`) appear only on **Assistant** and **Meetings**, the two pages whose banner holds the page's main action (the ask and call keys; Start recording). The test for adding one: if a plain settings row could hold what the banner holds, the page gets no banner. Home, AI cleanup and Dictionary had one each and lost it, because users found them distracting: Home's waveform said nothing its keys did not, and the paragraphs of word-bars on Cleanup and Dictionary read as loading skeletons. Home's dictation keys are now the first row of `ShortcutsCard`, and Cleanup's are a row of its own (`CleanupKeysRow`). The stage **follows the theme**: near-black on dark, a pale tinted surface on light. It used to be dark in both, and in the light window it was the highest-contrast thing on screen. `:root:not([data-theme="dark"]) .hero-stage` redefines every `--color-hero-*` token, so the utilities and controls on the stage follow without light variants of their own; it is scoped to the stage rather than `:root` because the onboarding tour draws hero keycaps on a faux desktop that stays dark. The headline is Instrument Serif (`<em>` in the translation string sets the italic; non-Latin locales fall back to Inter in CSS). The art is `src/assets/hero/<name>.webp` plus `<name>-light.webp`, chosen by `useHeroArt` (via `hooks/useResolvedTheme.ts`) and rendered by `scripts/hero-art.py` (numpy + Pillow, fixed seeds): as linear light on the dark stage and as Beer-Lambert ink on the light one, each on exactly its stage colour (`STAGE_DARK` / `STAGE_LIGHT` must match `--color-hero-surface` in each theme) so the CSS mask that fades it toward the text has no seam. Re-run the script rather than editing the files. The house style is flat: crisp shapes and nothing around them, no glow, bloom or depth of field (see `lens`), because every pass that only turned the glow down still read as glare. Keep the subject in the right ~60% and the far right edge clear, since the corner button sits there and Meetings' waveform used to run under it. The Assistant orb is deliberately the quietest piece, a rim around a sphere, because it sits above the longest settings list in the app. The art's only motion is a small entrance played once per banner per session (`.hero-art-enter`, removed by `Hero.tsx` when it finishes); keyed on `.page-layer-active` it replayed on every visit, because a hidden page is `display: none`. The live meeting recorder reuses the stage, and paused darkens the art on dark but only fades it on light: darkening or desaturating there shifts the image's own background off the stage colour and shows its edge. How-to text on a banner is a **tip**: anything in `HeroTip` starts folded, and the lightbulb opens it for the session (deliberately not persisted). Something the user must act on goes in `HeroShortcut`'s `status`, which never folds. Meetings' banner carries only Start; its models and switches are an ordinary settings group under it. The light theme as a whole is paper rather than a lightbox: an off-white pane (`--color-canvas` `#f3f6f6`) under white cards, and ink `#1b292e` (15:1 on a card instead of 18:1); the palette comment in `App.css` has the checked contrast pairs
  - `icons/` - Icon components. `ProviderLogos.tsx` holds the provider marks (simple-icons CC0 / LobeHub MIT paths, copied verbatim) behind `getProviderBrand(id, kind)` / `ProviderTile`; `BrandLogos.tsx` holds the model-family marks
- `assistant/` - The assistant's own window, in two modes. **The quick ask** (`QuickAsk.tsx`, state in `quickAskState.ts`) is one question and one answer: a single surface that is a pill while it listens or works, a bar while you type, and a card from the first streamed token, with Copy / Insert (Replace when the ask was about a selection) and no follow-up field. Copy and Insert put a formatted answer on the clipboard twice (`richAnswer.ts`): as HTML for rich editors (Word, Outlook, Gmail, Docs) and as its Markdown for everything else, Notepad and Markdown-aware fields like GitHub and Slack included; plain prose stays text only, and paragraphs carry `class="MsoNormal"` because Word reads a bare `<p>` as Times New Roman. Insert goes through the paste transaction like a dictation (`PasteRequest.html`): Windows promises `HTML Format` (`paste_tx::cf_html`) and macOS `public.html` beside the text, and a read of either is the receipt, since a rich editor reads only the HTML. **The call** (`CallBar.tsx`, `useVoiceConversation.ts`) is the conversation. **The two are one family and share parts rather than resembling each other**: the quick ask's waiting pill renders the call bubble's own `.call-level` bars and `.call-spin` spinner on the same chip surface and hairline, the status is one of four short labels (`workingLabelKey`: listening, thinking, searching the web, looking at your screen), and the one primary action in either is ink-filled. There is no badge and no accent colour. The pill used to carry a teal sparkle with a spinning ring, a teal edge, a teal waveform and "Screen" / "Selection" chips, five signals for "I'm on it" that none of the call's surfaces shared, so beside the call it read as another app. What an answer was about (a selection, the screen) is now said by chips on the card, where it explains the answer. `--as-accent*` survives only for a thumbnail hover and a few focus rings. **Answer typography is deliberate, and three of its four rules exist because the card was hard to read for reasons that are invisible when you look for a colour-contrast failure.** The measure is capped (`max-width: calc(68ch + 36px)`) because the card is as wide as the panel and a line of answer ran past 100 characters. Body copy sits on `--as-body` rather than the brightest `--as-ink`: near-white on near-black is ~15:1, far past any guideline, and at that ratio light glyphs bloom on an LCD — emphasis and headings step up instead, so hierarchy gets brighter rather than the paragraph. `overflow-wrap` is `break-word`, not `anywhere`, which was splitting ordinary words mid-glyph. And the markdown rules are **shared** with the thread bubbles (`.assistant-message-content, .ask-answer-body`): without that, the ask card fell back to the user-agent stylesheet — 1em paragraph margins, a 40px list indent, unstyled code and links — on the surface the hotkey actually opens. The size scale (`appearance.ts` `FONT_SIZES`) runs 13 / 14.5 / 16 / 18 px; it used to be 12.5 / 13.5 / 15, where the small→medium step was 1 px and the top of the scale was what the rest of the app calls default
- `reminder/` - Reminder popup window entry point (`ReminderPopup.tsx`). It **imports `AssistantPanel.css` and renders that stylesheet's own classes** — `.ask-card`, `.ask-head`, `.ask-question-text`, `.ask-action`, `.ask-answer-body` — the same thing the settings preview does, so a reminder does not resemble the assistant's card, it _is_ the assistant's card and cannot drift from it. `ReminderPopup.css` is only the handful of differences between a panel and a notification (the window is content-sized rather than filling a frame, and several reminders stack in it). Two mistakes worth not repeating, both from the first version: a lone amber accent — a 2px bar down the leading edge and an amber-filled Done button — read as a rendering artifact rather than as branding, because everything around it is monochrome; and Snooze as an absolutely-positioned popover opened straight through the bottom edge of the window and was clipped to a sliver, because the window height comes from the measured content and an absolutely-positioned element contributes none. The choices are in normal flow now, which makes that class of bug unreachable rather than fixed. Height is reported through `fit_reminder_popup` on a `ResizeObserver` (the stack grows three ways: another reminder, a wrapped line, the snooze row opening). Commands go through `invoke` rather than the generated `commands.*` wrappers, because `bindings.ts` is only regenerated while the app runs in dev
- `hooks/useSettings.ts` - Settings state management hook
- `stores/settingsStore.ts` - Zustand store for settings
- `bindings.ts` - Auto-generated Tauri type bindings (via tauri-specta)
- `overlay/` - Recording overlay window entry point. The live card draws committed text as append-only chunks, one element per extension, because React updates a changed string by rewriting its text node and that collapses any selection inside it. Updates wait while a press on the transcript is held and catch up on release, releasing a selection copies it (the window can never hold the keyboard, so Ctrl+C would reach the user's editor), and the body is exactly three lines tall so the top edge never slices a line in half. The working indicator (transcribing / cleanup) is **one forward-only fill, not a loop** (`overlay/workProgress.ts` + `progressWave`): a sweep that restarted every 1.6 s read as a loading bar failing to finish, over and over, on a long cleanup. The fill is budgeted from this machine's own history (a decaying fit of stage time on recording length, in `localStorage`), eases out gently within the estimate and creeps on a hyperbolic tail past it, and is capped at 94%, so only the real finish runs it out. **Its speed never jumps**: the drawn fill rides the curve through a critically damped spring on its offset _and relative speed_ (so a steady curve is followed with no lag; damping absolute speed trailed it by ~0.17s, over half a quick local dictation) and the finish is a Hermite run-out that starts at the current speed and lands at rest, as short as an acceleration cap allows (`sealDuration`, 120–280 ms) — the first version computed position straight from the curve and measured ×2.5 in speed at the cleanup hand-off and ×13 at the finish, which read as jerky and made a fast dictation feel slow (`workProgress.test.ts` bounds the per-frame change). **It ends with the text**: `paste_final` sends `seal-overlay` (`overlay::seal_working_overlay`) when the text is ready, before the paste, because the words appear at the keystroke and the paste's own tail (100 ms modifier hold, 50 ms clipboard restore) used to delay the run-out until the fill finished ~0.4 s after them; the compact pill's hold (`PILL_SEAL_HOLD_MS`) counts from that seal. The estimate's floor applies to the prediction, not the fit's intercept, which had lifted every estimate for a machine faster than the prior (0.51 s for waits of 0.30 s). **There is no completion mark**: a full, still row is the ending, because the pasted text is the real confirmation, and a tick drawn after every dictation read as slow and childish. The waveform freezes on that row while the window fades (`freeze`) instead of dropping to rest. `cleanupNext` on the transcribing show reserves cleanup's share so the bar does not fill and then start over. The compact pill holds `PILL_SEAL_HOLD_MS` after success so the run-out is seen. Flow's `generating` / `vision` keep the looping ripple, since nothing estimates them. **Hands-free** (`hands-free` on the pill or card) is a ring drawn in from the top at the moment the dictation turns, while the keys are still down, which is what tells the user they can let go, plus a pill a little longer than a held one. ✕ and ✓ appear only on hover, in room the longer pill already has: the waveform keeps its size and the window onto it narrows (squeezed, fourteen bars ran into one blob) while the padding grows by what the window loses, so nothing moves under the pointer and the window never resizes. On the card they join Copy, top right.

### Key Architecture Patterns

**Self-update does not need code signing.** The updater verifies a minisign signature made with our own free key (public half in `tauri.conf.json`, private half in the `TAURI_SIGNING_PRIVATE_KEY` / `_PASSWORD` repo secrets, key id `73D1FDFF87780381`). Apple/Azure code signing is a separate, paid thing that only affects first-install warnings. Until 2.0.0 the two were tied together in CI, and the app also trusted upstream Handy's key, so no release from 1.0 to 1.4 ever had a working update path — and the only update UI was rendered with `className="hidden"`. Now: `build.yml` keeps `createUpdaterArtifacts` whenever the key secret exists (`HAS_UPDATER_KEY`), re-signs the Linux AppImage and `.deb` **after** they are repacked (the bundler's signatures describe pre-repack bytes), and `updater-manifest.yml` writes `latest.json` once, at the end, from the `.sig` files actually on the release, verifying every signature against the published bytes (`scripts/ci/updater-manifest.ts`, tested with a real signature), then deletes those `.sig` files, because the signatures now live in `latest.json` and installed apps never fetch a `.sig`. A re-run (after re-building one platform) reads the signatures it no longer finds as files back out of the existing `latest.json` and verifies them the same way. tauri-action's own `latest.json` is off (`includeUpdaterJson: false`). Installed apps poll `releases/latest/download/latest.json`, which GitHub serves only from the newest published non-prerelease release, so a draft or a beta never reaches anyone. On the frontend, `update-checker/updateStore.ts` is the one state machine; `UpdateChecker` runs the checks (8 s after launch, then every 12 h; `update_checks_enabled` only disables the automatic ones), `UpdatePill` announces a found update at the bottom of the sidebar, and `UpdatePanel` in Settings → About shows notes and the install / download action for the install mode. **Losing the private key means installed apps can never update again** — it lives at `~/.tauri/speakoflow-updater.key` on the maintainer's machine and in the repo secrets; back it up.

**Feedback** is the "?" beside Settings in the sidebar, "Send feedback…" in the tray, and a row in Settings → About (`components/feedback/`). The draft is saved as it is typed, so closing the dialog or a failed send loses nothing. The Worker (`feedback-worker/`, deploy steps at the top of its `wrangler.toml`) validates with the same limits as the app, rate-limits per address and globally, defuses `@mentions`, and authenticates to GitHub as a GitHub App (issues opened by a bot, so the owner is emailed) or with a fine-grained PAT (issues opened as the owner, who is not emailed about their own activity by default).

**Manager Pattern:** Core functionality organized into managers (Audio, Model, Transcription) initialized at startup and managed via Tauri state.

**Command-Event Architecture:** Frontend → Backend via Tauri commands; Backend → Frontend via events.

**Pipeline Processing:** Audio → VAD → transcribe.cpp (streamed, long-form chunks, or one run; see `transcription/policy.rs`) or a cloud provider → Text output → Clipboard/Paste

**State Flow:** Zustand → Tauri Command → Rust State → Persistence (`settings_file.rs`, see Settings System)

**Custom Title Bar:** Native window decorations are disabled on Windows/Linux (`decorations(false)` in `lib.rs`); the webview draws the chrome via `TitleBar.tsx` (brand + minimize/close, which needs the `core:window:allow-minimize`/`allow-close` capabilities). macOS keeps the window decorated with an overlay title bar (`TitleBarStyle::Overlay` + `hidden_title`) so the native traffic lights still work. Close hides to the tray (see `on_window_event`).

**Paste Safety Net:** Synthetic-paste flows (`input.rs`) always release modifiers after a key combo, via `input::release_all_modifiers`, so an interrupted paste can never leave Ctrl/Shift/Alt/Cmd stuck "pressed" at the OS level.

**The clipboard goes back only after the target read the dictation** (`paste_tx/`, Handy #1812 / #1847; Windows and macOS). The plain paste put the user's clipboard back a fixed 50 ms after Ctrl+V, but the keystroke is only queued by then, and a busy target (a browser tab, an Electron editor, a loaded machine) read the clipboard late and pasted whatever the user had copied before. Now the dictation is published as a promise (Windows delayed rendering, answered on `WM_RENDERFORMAT`; macOS `declareTypes:owner:`), and a read is the receipt. Only reads after the keystroke count, since earlier ones are a clipboard manager or remote-desktop client reacting to the change. The restore waits `QUIET_PERIOD` after the last read (Chromium probes, then reads), is capped by `RESTORE_TIMEOUT`, and only happens while the clipboard is still ours, so a copy the user made meanwhile wins. A promise already read before the keystroke falls back to `BLIND_RESTORE_DELAY`, so a clipboard manager does not make every paste wait the full timeout; its auto-submit Enter goes on its own, much shorter `BLIND_SUBMIT_DELAY` (`blind_submit_due`), not with the restore. A pending paste is settled before an ask's selection harvest, dropping any Enter it still owes, because the ask's keys are held at that moment (on macOS this runs on the main thread and is waited for briefly), and before exit (`settle_before_exit`, from `release_before_exit`). The Windows snapshot reads the text first, never reads OLE bookkeeping formats (they make Office render embedded objects while the paste waits), and stops after `SNAPSHOT_BUDGET` / `MAX_SNAPSHOT_BYTES`, restoring in the original format order. Auto-submit's Enter moves into the transaction and is sent only once the target has read the text. The failure mode is always "the dictation stays on the clipboard a few seconds longer", never "the old clipboard gets pasted". `clipboard::paste_via_transaction` falls back to the plain paste when the transaction cannot start (`PasteTxError::Unavailable`), Linux always uses the plain paste, and `snapshot_clipboard` calls `settle_pending` first so an ask's selection harvest never records a pending dictation as the user's clipboard.

**Synthetic input must not be read back as a hotkey.** Every synthetic key sequence in `input.rs` and `clipboard.rs` opens `input::synthesizing()`, which raises a counter the vendored handy-keys Windows hook consults (`vendor/handy-keys/src/injected.rs`); an `LLKHF_INJECTED` event arriving while it is up is passed through to the target app but withheld from hotkey matching. Without it the assistant's hold-to-talk recorded nothing: `AssistantAction::start` harvests the focused app's selection with a synthetic Ctrl+C, and the injected Ctrl key-up matched the modifier-only `Ctrl+Alt` binding as a release, ending the recording ~30 ms after it began. `input::conflicting_modifier_held` was written to prevent exactly that and could not, because it asks `GetAsyncKeyState` whether Alt is down and the hook had _blocked_ that Alt key-down from ever reaching Windows — the blind spot is now documented on the function. The guard is a window rather than a blanket `LLKHF_INJECTED` filter so a macro keyboard or accessibility tool that fires a registered hotkey still works. `send_copy_combo` additionally borrows a Ctrl the user is already holding instead of pressing and releasing its own, which would desync the OS from the key still under their finger.

**Dictating into our own main window is an event, not a paste.** `paste_final` holds the main thread from writing the clipboard through restoring it, and a webview's Ctrl+V is only handled once that thread is free, by which time the clipboard is back to the user's content, so a paste into any field of the main window (onboarding's try-it box, a search field) silently did nothing while every other app worked. When the main window is focused and the recording did not start in another app (`delivers_in_app`), the final text is sent as `dictation-into-focus` and `src/lib/insertDictation.ts` inserts it at the caret with `execCommand("insertText")`, which React's controlled fields and the undo stack both see.

**Paste target:** a synthetic Ctrl+V reaches whatever holds keyboard focus at the instant it is sent, and the gap between the shortcut and the paste is a whole recording plus a transcription plus an optional LLM pass. `input::remember_paste_target` records the foreground window at recording start (`TranscribeAction::start`) and `restore_paste_target` hands it back from `clipboard::paste_with_behavior` — but **only when one of our own windows took the foreground**, which is the unambiguous failure and also the only case Windows lets us repair, since `SetForegroundWindow` is granted to the process that already owns the foreground. A switch to a _different application_ is logged and respected: someone who alt-tabs mid-dictation usually means to dictate into the window they switched to, and stealing focus back would be a worse bug than the one being fixed. A foreground window that is ours at recording start records no target, so the in-app dictation paths are untouched. Windows-only by construction: the overlay is a non-key NSPanel on macOS and a `KeyboardMode::None` layer surface on Wayland, so neither can take focus in the first place.

**Personal Memory (local-first):** `memory.rs` maintains a two-tier profile — an always-on "About You" summary plus durable notes selected by keyword relevance within a per-turn character/token budget (the `MemoryDetail` dial: Light/Balanced/Detailed). `build_memory_block` appends an advisory, delimiter-wrapped block late in the prompt in `run_assistant_turn` (kept late so the earlier prefix stays cache-friendly). Learning ("distillation") runs OFF the hot path at the end of a conversation — when the panel is hidden (`hide_assistant_panel`), the conversation is cleared (`assistant_clear_conversation`), or the user clicks "Update memory" (`assistant_distill_memory_now`) — reusing the active assistant provider (which can be the fully-offline built-in engine). A `last_distilled_len` dirty-guard prevents redundant passes. Safety is layered: capture, consolidation, and injection all reject secrets/PII and instruction-shaped text (`is_sensitive`), injected memory never overrides the user's current message, and consolidation dedupes/merges (Jaccard overlap), decays stale low-confidence auto notes (~45 days), and prunes to a hard cap. Off by default; an Incognito toggle skips both use and learning for a conversation. It's all stored on-device in settings and fully user-editable/exportable in Settings → Memory.

**Screen Vision (two switches, the model decides):** screen access is two settings, one per surface — `assistant_ask_screen_access` (the quick ask) and `assistant_call_screen_access` (a call), both **off by default** because a screenshot goes to whichever provider the user chose. On does not mean "capture": it means the turn is offered the `capture_screen` tool (`screen_access_for_turn`, never for the Cat persona) and the model decides per message. What it decides with is `screen_tool_guidance`, and the wording is the feature: look when the user asks ("look at my screen") or when the message is about something visible it was not given as text ("this error", "reply to this email"); never for anything answerable blind (general knowledge, writing, the time, reminders); and text inside `<selected_text>` **is** the "this" — answer from it and do not look unless explicitly asked. The previous guidance keyed on phrases like "what does this mean" and said nothing about selections, so "select three words, ask what this is" matched it exactly and screenshotted the desktop. The tool is deliberately _not_ withheld when a selection is present, because that also made "look at my screen" impossible with text selected. There used to be a third mode, **Manual** (a camera toggle and a region snip in the typed bar, with its own authorization tokens, an armed flag, a snip overlay window and a pending-attachments mirror); it and all of that machinery are gone, and `normalize_settings_json` migrates stores conservatively — only `agent_decides` turns the switches on; Manual (the old default) and Off turn them off, since the alternative would start sending screenshots nobody agreed to send. `screenshot.rs` captures the monitor under the mouse cursor (`capture_screen_data_url_at`) and adaptively JPEG-compresses to the provider's payload budget (verified against Azure's tight cap). `VisionCaptureTiming` only changes _when_ the frame is taken, never whether it is sent: `Immediate` (default) parks one at recording start in `AssistantAction::start` (`begin_agent_capture`, quick ask only), `OnSend` starts it at the top of the turn (`ensure_agent_capture_started`), and a frame the model never asks for is dropped at the end of the turn (`clear_agent_capture`) without leaving the device. A call never pre-captures — every utterance is a turn, so that grabbed the screen continuously — and `agent_capture_screen` captures on demand instead, re-checking the asking surface's switch at dispatch. Every screenshot the model takes adds the screenshot marker and a persisted display thumbnail (`ChatMessage.images`) to the user message, shown inline in the panel and history with click-to-enlarge; only that thumbnail persists, and the full-resolution frame is sent once.

### Application Flow

1. **Initialization:** App starts minimized to tray, loads settings, initializes managers
2. **Model Setup:** First-run setup offers five speech models (`SETUP_SPEECH_OPTIONS`, Parakeet for English and Nemotron for other languages recommended) and downloads only the one picked
3. **Recording:** Global shortcut triggers audio recording with VAD filtering
4. **Processing:** Audio transcribed by the selected model on transcribe.cpp (or a cloud provider), streaming as it records when the model streams
5. **Output:** Text pasted to active application via system clipboard

### Settings System

Settings live in `settings_store.json`. `settings_file.rs` owns that file rather than `tauri-plugin-store`. Every save is atomic: it writes a temporary file, fsyncs it and renames it over the old one, and the create and the rename are retried for up to ~450 ms when another process holds the file (Defender, the search indexer or a sync client on Windows). Damaged **content** (empty, NUL bytes, not JSON, not an object; a UTF-8 BOM is not damage) is moved aside to `.corrupt-<time>`, of which the newest five are kept, and the settings come back from `settings_store.json.bak`, which every launch that read a good file with a `settings` object refreshes when it differs. A first launch, which has no backup, gets one from its first save that holds settings; no save ever replaces an existing backup, so a restore brings back the settings as the last good launch found them and the notice says recent changes may be missing. A file that parses but lost its `settings` object takes that entry back from the backup and keeps its other keys, so the defaults `get_settings` would write can never reach the backup on the next launch. A read **error** is not damage: after a few retries the file is left where it is, nothing is saved that session, and the session runs on the backup's settings or the defaults. Each of these outcomes, and saves that fail three times in a row or for ten seconds, becomes a `SettingsNotice`. The file is read before any window listens, so the main window fetches the current notices on mount (`get_settings_notices`), hears later ones on `settings-notices`, and shows them as toasts (`hooks/useSettingsNotices.ts`); a dismissed notice is not shown again on reload. Two rules matter. **Never open that file with `app.store()`**: the plugin would keep its own copy and write it back non-atomically on exit. **Go through `settings::settings_file(app)`** for any other key kept in that file (the meeting pill position, for example). The plugin's in-place `fs::write`, together with a load that silently ignored a damaged file, is how a shutdown reset every setting. What the settings cover:

- Keyboard shortcuts (configurable, supports push-to-talk)
- Audio devices (microphone/output selection)
- Model preferences (`selected_model`, `selected_language` as an intent, `chinese_script`, `long_form_chunking`, and where speech runs: `transcribe_accelerator` + `transcribe_gpu_device`)
- Audio feedback and translation options

### Single Instance Architecture

The app enforces single instance behavior — launching when already running brings the settings window to front rather than creating a new process. Remote control flags (`--toggle-transcription`, etc.) work by launching a second instance that sends args to the running instance via `tauri_plugin_single_instance`, then exits.

## Platform Notes

- **macOS**: Metal acceleration (Apple silicon; Intel builds are CPU-only), accessibility permissions required for keyboard shortcuts
- **Windows**: Vulkan acceleration (x64; the ARM64 build is CPU-only, and the x64 build emulated on ARM keeps speech on the CPU), code signing
- **Linux**: Vulkan, limited Wayland support. **The SpeakoFlow keys engine is handy-keys' own evdev engine** (`vendor/handy-keys/src/platform/linux/engine.rs`), not rdev's grab: rdev's ended for good whenever an input device appeared (udev had not handed the new node over yet, `EACCES`), so a keyboard reconnecting killed every shortcut until a restart, and it took every device over at once, so a key held at that instant (Super, opening the app with Super+S) stayed pressed in the compositor. The engine takes a keyboard over only while no key on it is held (checked again right after `EVIOCGRAB`), after its uinput mirror has had `MIRROR_SETTLE` to be opened; withholds a key's repeats and release exactly when it withheld the press (`tracker.rs`); only reads pointers and devices other programs made through uinput; retries a node udev has not settled on `IN_ATTRIB`; drops a device that goes away without touching the others; and forwards libevdev's `SYN_DROPPED` resync. It needs no X display, so `shortcut/environment.rs` no longer reports a missing `DISPLAY`. Without `/dev/uinput` access shortcuts still fire, but their key also reaches the focused app. Its live tests (`cargo test -p handy-keys --lib -- --ignored --test-threads=1`) only ever touch their own virtual keyboards, but any new input node ends an older build's rdev grab, so stop a running copy of the app first. The overlay uses GTK layer shell (disable with `SPEAKOFLOW_NO_GTK_LAYER_SHELL=1`).
