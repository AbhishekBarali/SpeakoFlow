# AGENTS.md

This file provides guidance to AI coding assistants working with code in this repository.

## Development Commands

**Prerequisites:**

- [Rust](https://rustup.rs/) (latest stable)
- [Bun](https://bun.sh/) package manager

**Core Development:**

```bash
# Install dependencies
bun install

# Run in development mode
bun run tauri dev
# If cmake error on macOS:
CMAKE_POLICY_VERSION_MINIMUM=3.5 bun run tauri dev

# Build for production
bun run tauri build

# Frontend only development
bun run dev        # Start Vite dev server
bun run build      # Build frontend (TypeScript + Vite)
bun run preview    # Preview built frontend
```

**Linting and Formatting (run before committing):**

```bash
bun run lint              # ESLint for frontend
bun run lint:fix          # ESLint with auto-fix
bun run format            # Prettier + cargo fmt
bun run format:check      # Check formatting without changes
bun run format:frontend   # Prettier only
bun run format:backend    # cargo fmt only
```

**Model Setup (Required for Development):**

```bash
mkdir -p src-tauri/resources/models
curl -o src-tauri/resources/models/silero_vad_v4.onnx https://blob.handy.computer/silero_vad_v4.onnx
```

For detailed platform-specific build setup, see [BUILD.md](BUILD.md).

## Architecture Overview

SpeakoFlow is a cross-platform desktop voice assistant (dictation, AI chat panel, screen vision, and a local-first personal memory) built with Tauri 2.x (Rust backend + React/TypeScript frontend). It started as a fork of [Handy](https://github.com/cjpais/Handy) by CJ Pais; the local dictation core (Whisper/Parakeet pipeline, VAD, overlay, settings architecture) traces back to that project. See [README.md](README.md#credits--license) for full attribution.

### Backend Structure (src-tauri/src/)

- `lib.rs` - Main entry point, Tauri setup, manager initialization
- `managers/` - Core business logic:
  - `audio.rs` - Audio recording and device management
  - `model.rs` - Model downloading and management: resilient downloads that auto-retry with exponential backoff and resume from a `.partial` file via HTTP `Range` (`attempt_download`, `AttemptOutcome`, `HttpStatusError` sorting transient vs. permanent failures), plus an ordered source list — a reliable mirror first, the canonical Hugging Face URL as fallback (`download_candidates` / `mirror_url_for`; mirrors not yet populated). It also owns **SpeakoFlow Mini** (`SPEAKOFLOW_MINI_MODEL_ID`), our own 0.8B English dictation-cleanup fine-tune. It is a `LlamaCpp` model but not a chat model, and `is_cleanup_specialist` is what encodes that: the predicate matches a normalized model _name_, not just the catalog id, so the same weights are recognized whether they arrived as the bundled download, a `.gguf` the user imported, or a model served from their own Ollama/LM Studio endpoint. Being a specialist changes three things — the cleanup catalog features it, the assistant catalog hides it (it cannot converse), and the request path drops the app's own prompt scaffolding. The derived flag reaches the frontend through `ModelInfo.is_cleanup_specialist`, stamped in `get_available_models` / `get_model_info` rather than at the ~30 construction sites so every insert path is classified by one rule
  - `transcription.rs` - Speech-to-text processing pipeline. Compute-device enumeration is crash-isolated on Linux: `PROBE_DEVICES_OUT_OF_PROCESS` (true only on Linux) sends `cached_gpu_devices` / `cached_transcribe_cpp_devices` through `probe_devices_out_of_process`, which spawns `self --probe-devices` and parses one line of JSON. The vendored, statically linked whisper.cpp/ggml in `transcribe-rs` uses ggml's default `GGML_NATIVE=ON` (`-march=native`) unless told otherwise, so a build tuned to one CPU can raise SIGILL in its Vulkan backend on a narrower one. Release CI therefore exports `GGML_NATIVE=OFF` (a fixed AVX2 + FMA + F16C + BMI2 baseline on x86-64; whisper-rs-sys forwards every `GGML_*` env var to CMake, and does not rebuild when it changes, hence the `-ggml-portable` cache key), and `whisper_cpu_supported` refuses Whisper with a message on a CPU below that baseline instead of crashing. On Linux a crash during device listing still happens out of process, so it costs a GPU listing instead of the whole app at launch. Windows/macOS keep the in-process call unchanged
- `managers/history.rs` - Transcription history storage, and the **recording-retention policy**. `resolve_retention_plan(period, limit, custom_days, now)` is a pure function returning a `RetentionPlan` (`KeepAll` / `ByCount` / `OlderThan`) — the clock is a parameter so every branch is unit-testable, because every bug this feature had was in the decision rather than in the SQL. `apply_plan` prunes in **one transaction on one connection** and unlinks WAVs only after the commit, and only once no surviving row references them; it previously opened a second connection and committed once per row, so a `SQLITE_BUSY` against the concurrent insert in `save_entry` failed the settings command _after_ the value was already written. `count_pending_deletions` is the dry run the UI uses to say "this deletes N recordings" before anything is destroyed. Three months means three **calendar** months (`chrono::Months`), not the `3 * 30` days the old code used and admitted was approximate. Enforcement happens at four points, not one: launch, a 30-minute sweep in `lib.rs`, after every `save_entry`, and when the History panel mounts (`enforce_recording_retention`) — with only the first two, an age policy never fired on a machine where the app stays open and no new dictation lands, so entries crossed their cutoff and stayed listed, which reads as the setting doing nothing
  - `local_models.rs` - Registering models the user **already has on disk**, so an existing collection or a self-made fine-tune needs no re-download and no hand-copying (issue #18). Two entry points, one destination: pick a file, or link any number of folders (`settings.model_folders`) that are then scanned recursively (`scan_folder`, bounded by `MAX_SCAN_DEPTH` / `MAX_SCAN_ENTRIES`, symlink-loop guarded). The hard part is **classification**, and it is done by content rather than filename, because a bare `.gguf` doesn't say whether it's speech-to-text, a chat model, or a vision projector that isn't a standalone model at all: `classify_model_file` reads `general.architecture` from the GGUF header (via `gguf_meta`) and routes an arch in `model_capabilities::KNOWN_ARCHES` to `TranscribeCpp`, a `clip`/`mmproj` arch to a projector (rejected on its own, auto-paired when it sits beside an LLM), and anything else to `LlamaCpp` — an unknown arch is far more likely to be a new chat model than a broken file. A `.bin` is validated against the ggml magic and treated as Whisper. On the `model.rs` side, `ModelInfo.local_path` / `local_folder` carry the result and every path-resolution site (`get_model_path`, `update_download_status`, `apply_gguf_header_hints`, `resolve_mmproj_path`, `local_llm::gguf_path_for`) reads the user's path instead of `<models_dir>/<filename>`. The standing invariant: **these files are not ours** — registering copies nothing, `delete_model` only unregisters, and a folder-derived entry refuses individual removal (the next scan would re-add it) and points at unlinking the folder instead. Only individually picked files are persisted (`local_models.json`); folder contents are re-derived on every scan so a model added to or deleted from a linked folder appears or disappears on its own
- `audio_toolkit/` - Low-level audio processing:
  - `audio/` - Device enumeration, recording, resampling
  - `vad/` - Voice Activity Detection (Silero VAD)
- `commands/` - Tauri command handlers for frontend communication
- `cli.rs` - CLI argument definitions (clap derive)
- `shortcut/mod.rs` - Global keyboard shortcut handling (two engines: `handy-keys` and the Tauri global-shortcut plugin). Both engines route through the shared `shortcut/handler.rs::handle_shortcut_event`, which resolves the recording mode via `transcription_coordinator::recording_mode`. Every recording shortcut (dictation, dictation + post-processing, and the assistant) follows the single `push_to_talk` setting: on means hold to record, off means tap to start and tap to stop. There is no second, hands-free variant of any shortcut. **The defaults are one scheme on every platform**: two keys to dictate (Windows Left Ctrl + Win, macOS Fn, Linux Ctrl+Space), two to ask (Left Ctrl + Left Alt, Fn+Ctrl, Ctrl+Alt+Space), the dictation keys plus Shift to dictate and clean up, the ask keys plus C to start a call, and Esc to cancel. Linux has a main key in every combo because its default engine (Tauri's plugin) cannot register a modifier-only one. The Windows ask has to contain Ctrl: the ask harvests the selection with a synthetic Ctrl+C while the keys are still held, which only works because Ctrl is already part of that combo and the other key is withheld from Windows. **Shortcuts that share their first keys (Ctrl+Alt and Ctrl+Alt+C; Fn and Fn+Ctrl) are resolved in two places, one per recording mode.** With Tap to toggle, the vendored handy-keys manager fires modifier-only hotkeys when their keys are _let go_ (`HotkeyManager::set_fire_on_release`, set from `push_to_talk` at launch and by `handy_keys::apply_recording_mode` when it changes): letting go with nothing pressed in between is the tap, and any other key in between was another shortcut, so that one never fires. There is no timer, which is why it holds however slowly the C follows; a fixed 200 ms grace was tried first and a deliberate Ctrl, Alt, pause, C beat it every time, so every call still opened the ask's panel on the way. With Hold to talk the press has to start recording at once, so the manager fires on press and withdraws the hotkey with `HotkeyState::Cancelled` when a keyboard key follows within `CHORD_CANCEL_WINDOW` (400 ms); `handle_shortcut_cancelled` turns that into a coordinator `Abort` that discards the recording without an Undo offer (`utils::discard_aborted_recording`). What such a press would _show_ waits for that window (`shortcut/chord.rs`: `holds_back` when another live shortcut extends this one's keys, `reveal_when_settled`, `reveal_now` on release, `forget` on withdrawal), so the recording runs from the first moment but its pill or panel never flashes up on the way to another shortcut. That is also why ending a running call is part of the ask's reveal rather than its press: the call key starts with the ask's keys, and ending the call on the press meant the call key could never hang up. The Windows hook then replays the modifiers it had withheld in front of that key (`replay_chord`), so VS Code gets Ctrl+Alt+↑ and a German layout gets Ctrl+Alt+Q = `@` instead of Ctrl+Q; and when it blocks the last modifier of a combo whose earlier Win or Alt Windows did see, it taps the unassigned vk 0xE8 so releasing that key opens no Start menu or menu bar. Its own injections carry `OWN_INJECTION_MARKER` and pass straight through. **Cancel and the call are removable** (`settings::OPTIONAL_BINDINGS`). A shortcut row at rest shows only its keys; clicking them opens the editor, which is the only place "Use default" and, for these two, "Turn off" appear (`ShortcutEditActions`), so neither can be hit by accident, and turning off is announced with an Undo. Esc is not how the editor closes, since Esc is itself a key you may want to record; clicking elsewhere leaves it unchanged. Dictation and the ask always keep a key. An empty Cancel is only migrated to Esc once, from installs that predate the Esc default, so a removed Cancel stays removed. `migrate_binding_defaults` moves any binding still on an older default to the new one, except on macOS, where an install still on the old Option-based defaults keeps them (`keeps_previous_default`), because the Fn key needs "Press 🌐 key to" set to Do Nothing first; the Home shortcuts card says so when it is not (`globe_key_has_own_action`). The handler also routes the cancel/`Esc` binding to either an active recording or a busy assistant reply
- `settings.rs` - Application settings management (recent additions: `sound_theme`; the experimental AI-Correction fields `post_process_enabled` / `post_process_tone` / `post_process_timeout_secs` / `post_process_unload_timeout` — cleanup keeps its **own** engine-residency policy, separate from the assistant's `local_llm_unload_timeout`; and the `experimental_enabled` gate that hides in-development features). **AI-cleanup prompting is a fixed two-layer hierarchy**: layer 1 is the selected cleanup system prompt (`post_process_selected_prompt_id` → `post_process_prompts`, which decides what gets corrected), layer 2 is the writing style (`post_process_selected_tone_id`, layered on top, which decides how the result reads). A third layer — the app's own final-output contract — is appended last and only for a general-purpose model. The former `post_process_cleanup_strength`, `post_process_fix_misheard`, and `post_process_raw_prompt` settings are **gone**: the first two were extra prose competing with the prompt for a small model's attention, and the third asked the user to know something the app derives (see `ResolvedPostProcessConfig::trained_for_cleanup`). Two bundled prompts ship: the long general-purpose one (`DEFAULT_POST_PROCESS_PROMPT_ID`) and the short one SpeakoFlow Mini was trained on (`SPEAKOFLOW_MINI_PROMPT_ID`); `restore_post_process_prompt` puts either back to its shipped text. `post_process_last_cloud_provider_id` / `assistant_last_cloud_provider_id` persist the cloud provider that the "On my device" switch would otherwise erase — both provider ids are single slots, so this is what makes the device ⇄ cloud switch restore a real choice instead of guessing. `assistant_enabled` (default true) is the master switch for the assistant: off means the panel window is never created at launch (and is destroyed, not hidden, when it is turned off), its two bindings — `assistant::ASSISTANT_BINDINGS`, enforced in `shortcut/handler.rs`, unregistered by `set_assistant_enabled`, skipped at launch by both engines' `init_shortcuts`, and refused for external/CLI triggers in `signal_handle::send_transcription_input` — do nothing, the assistant's llama.cpp process is stopped rather than left to idle out, and Profiles/Memory disappear from Settings. "Generate with Flow" and AI Correction deliberately survive it: they share `assistant_provider_id` / `assistant_models`, so the brain picker stays visible. The built-in provider declares `supports_structured_output: true`: llama.cpp compiles the JSON schema into a decoding grammar, which is what stops small chat models from narrating their plan instead of returning the cleaned transcript (measured on Gemma 4 E2B: 400 tokens of monologue without it, a correct 48-token answer with it) — and it is deliberately **not** sent to a cleanup fine-tune, which was trained to emit bare text and would be forced into JSON by the same grammar
- `managers/local_llm.rs` - Bundled llama.cpp sidecar. **Two engine instances, one per `LlmRole`**: `Assistant` (port 11435, vision projector, full context) and `Cleanup` (port 11436, no projector, context capped at `CLEANUP_CONTEXT_SIZE`, `LLAMA_ARG_THINK_BUDGET=0`). Sharing one engine meant a different model on either side evicted the other on every use. **Both roles take the GPU** (`ALL_GPU_LAYERS`): cleanup used to pass `-ngl 0` for small models because a cold load is ~2x faster on CPU and skips the one-time 13–20s shader compile, but that optimised the wrong half — measured on a 2B Q8*0, generation runs at ~212 tok/s on a dedicated GPU against ~21.8 tok/s on the CPU, and generation is what happens on every dictation, while the load happens once behind `warm_up()`. Device \_selection* is pinned with `--device`, not `--main-gpu`: the latter does not choose where the model runs (measured on a 4070 Ti SUPER + Ryzen iGPU box, `--main-gpu 1` still ran on the dedicated card), so on any machine whose ggml device 0 is the integrated GPU the engine silently ran there at ~7 tok/s. `pinned_device_arg` / `select_engine_device_arg` resolve the flag from the engine's **own** `--list-devices` output (`parse_engine_devices`, cached per run) matched against our probe by adapter description, because the two enumerations are independent and their order need not agree. It only engages on a mixed dedicated + integrated machine (`needs_device_pinning`) — elsewhere the engine's own choice is already right and multi-GPU layer splitting is left intact. `warm_up()` sends a synthetic prefill so page-in and GPU pipeline compilation happen during recording rather than on the user's first cleanup. **The engine version is pinned, not looked up** (`PINNED_ENGINE_TAG`, b11429): it used to ask GitHub for `releases/latest`, but llama.cpp marks every real `bNNNNN` build a prerelease, so "latest" became a `v0.6.0` stub with only `nightly-tag.txt` in it and every install silently fell back to b10075, which aborts Gemma 4 E2B/E4B on `GGML_ASSERT(n_inputs < GGML_SCHED_MAX_SPLIT_INPUTS)` whenever the graph is split across backends (fixed upstream in b10247). Archive names are exact per OS/arch (`pinned_asset_names_for`, Vulkan first, CPU as the fallback; Windows on ARM stays CPU-only). To bump the pin, check every archive exists in the new release and re-test chat, vision, tool calls, JSON-schema output, `LLAMA_ARG_THINK_BUDGET=0` and the `--list-devices` format; every install re-downloads once because `engine.tag`, which records the tag of the archive actually unpacked, no longer matches. `HANDY_LLAMA_RELEASE_TAG` overrides the pin and `HANDY_LLAMA_SERVER` bypasses the managed engine. Both roles share `models/engine/`, so install and replace run under one process-wide lock (`engine_install_lock`) that re-checks the stamp after acquiring it, and a stale engine the other role is running from is reused rather than deleted (Windows cannot delete a running engine's DLLs, and an engine this process started already passed the check). The engine logs at trace level (`LLAMA_ARG_LOG_VERBOSITY=4`: layer offload, buffer sizes and the scheduler's split count, about 30 lines per request, no prompt text) and also to its own file (`LLAMA_ARG_LOG_FILE`, `llama-server[-cleanup]-debug.log` beside the console capture), both set by env var so a build that predates them still starts; a start failure quotes the console tail plus any lines only the engine's own file has
- `secret_store.rs` - API keys in the OS keychain (`keyring`), hydrated into settings on load
- `stt_cloud.rs` - **Cloud speech-to-text**: transcription on a hosted API instead of a local model, gated on `SttEngineMode::Cloud` (default `Local`, so an existing install is untouched). Five services ship configured plus a free-form OpenAI-compatible entry, and `CloudSttKind` is a real protocol dispatch rather than a label — "OpenAI-compatible" is near-universal for chat but not for transcription: ElevenLabs authenticates with `xi-api-key` and calls the field `model_id`, Deepgram takes the audio as a **raw request body** with every option as a query parameter and no multipart envelope at all. Two decisions carry most of the weight. First, requests run on a **dedicated thread with their own current-thread runtime** (`block_on_request`), because `TranscriptionManager::transcribe` is synchronous and its callers straddle the runtime boundary — `actions.rs` calls it from inside an async task while history and voice-conversation come in via `spawn_blocking` — so neither `tauri::async_runtime::block_on` nor `reqwest::blocking` is safe under both. Second, an incomplete cloud configuration resolves to `Err` and **falls back to the local engine** instead of failing the dictation; only a _complete_ configuration that then fails on the wire surfaces an error, because at that point there is no loaded local model to fall back to. `batch_model_id` maps `scribe_v2_realtime` → `scribe_v2` so the batch fallback still works for a user configured for streaming, which is exactly when the fallback matters. Custom words are forwarded as provider-native biasing (ElevenLabs `keyterms`, OpenAI `prompt`, Deepgram `keyterm`), and when they are, the local fuzzy-correction pass is skipped — a second pass over text the model already got right can only corrupt it
- `stt_cloud_stream.rs` - Realtime cloud STT over WebSockets (ElevenLabs Scribe v2 Realtime, Deepgram). `CloudStreamSession` is a deliberately **blocking facade** owning its own current-thread runtime, so it drops into the transcription manager's existing `feed`/`finalize` worker shape instead of forcing an async rewrite; the socket needs no background pump because `feed()` is called ~30x/sec and drains what has already arrived via `now_or_never()`. ElevenLabs runs with `commit_strategy=vad` so segments close at natural pauses — that is what produces an append-only committed prefix instead of one enormous commit at the end — and the final flush sends the tail with `commit: true`. Provider partial/committed events map onto the overlay's existing `committed`/`tentative` split, published through a `LiveTextSink` closure rather than an `AppHandle` so the protocol logic has no dependency on the window layer (and can be driven by a live test). Streaming support is checked against the **model**, not just the provider, because ElevenLabs' realtime and batch endpoints have separate model namespaces. A partial can arrive after the commit that closed its segment, and taken at face value it became the new tail, which is how two dictations were pasted with the whole transcript repeated, the second copy ending in an earlier guess. `LiveTranscript` drops a partial that repeats the segment just committed, judged by order-aware word overlap, and never drops a commit, since someone who says a sentence twice means it twice. Every failure is non-fatal and answers `None`, routing `finalize_stream()` to the complete batch transcription
- `stt_cloud_live_tests.rs` - `#[ignore]`d live checks against a real ElevenLabs key (batch, realtime, the verification probe, and the bad-key message). Offline unit tests can only prove this app parses what it expects; whether the endpoint accepts what it _sends_ has one authority. The key comes from `ELEVENLABS_API_KEY` or the app's own keychain slots, and the audio from the newest saved recording, so `cargo test --lib stt_cloud_live -- --ignored --nocapture` needs no setup on a machine that already has ElevenLabs configured

Two traps worth knowing before touching the cloud-STT settings UI. First, **`updateSetting` is an allowlist, not a generic writer**: `settingUpdaters` in `src/stores/settingsStore.ts` maps a settings key to the command that persists it, and a key with no entry updates the store optimistically and then only `console.warn`s — the value looks saved and evaporates on the next refresh. Every `cloud_stt_*` field therefore goes through its own command (`set_cloud_stt_provider` / `_model` / `_base_url` / `_streaming` / `_send_custom_words` / `_no_verbatim`), per-provider rather than whole-map so two edits cannot clobber each other's provider. Second, **every wait in `stt_cloud_stream.rs` must be bounded**: `feed()` runs on the thread draining the audio channel, so an unbounded `block_on` leaks that thread and the socket. Note also that `now_or_never()` is the wrong way to poll this socket — a future that is never `Pending` means `block_on` never parks, and a current-thread runtime only ticks its I/O driver on park, so a "non-blocking" read can report nothing while data sits waiting; `DRAIN_POLL` is small but deliberately non-zero.

**OpenRouter needs two registry fields, not a new protocol.** It reaches ~20 transcription models (Whisper, GPT-4o-transcribe, Deepgram Nova-3, Google Chirp 3, MAI-Transcribe, Voxtral, Parakeet, Qwen ASR, Grok STT) behind one key and accepts the OpenAI multipart shape, so `CloudSttKind::OpenAiCompatible` covers the wire format. `models_endpoint` carries the discovery path **including its query string**, because OpenRouter excludes transcription models from the default `/models` catalog and only returns them for `?output_modalities=transcription` — a bare `/models` there lists hundreds of chat models and not one that can transcribe. A listing already scoped that way also skips the `looks_like_transcription_model` name heuristic, which would otherwise drop correctly-listed models whose slugs say nothing about the task. `honors_keyterms` is false for OpenRouter because it documents `prompt` as accepted-but-ignored on the multipart route: without that flag the app would believe it had biased the request upstream, skip its own fuzzy custom-word pass, and apply neither correction. Slugs there are namespaced `vendor/model` and must not be rewritten. `ensure_cloud_stt_defaults` also normalizes provider **order** to the shipped registry, so a store upgraded across versions doesn't show a new provider appended after "Custom" while a fresh install shows it before.

**Cloud transcription latency is connection setup and a cold provider route, not upload.** Measured against OpenRouter from Nepal (`stt_cloud_bench`, all `#[ignore]`d): WAV encoding is 12 ms and client construction 0.4 ms, both irrelevant. Latency does **not** scale with payload — a six-length least-squares fit on `mai-transcribe-2` put the uplink at ~1.5 MB/s, i.e. 0.02 s per second of speech, so even a 60-second dictation spends about a second uploading on a fast link. That held for a desktop on wired broadband and did not hold on a laptop: on a ~1 Mbit/s Wi-Fi uplink a five-minute WAV (9.6 MB) took ~77 s to upload, longer than the fixed 60 s timeout, so long dictations to batch-only providers (Azure MAI-Transcribe) fell back to the local model. Batch uploads are therefore **48 kbit/s MP3** (`encode_mp3_16k_mono`, LAME via `mp3lame-encoder`, 5.3x smaller; measured as no WER change against WAV on 6,559 LibriSpeech words) for every hosted provider, and WAV only for the custom endpoint and for a route that answered MP3 with a media-format error (`is_format_rejection` → `remember_mp3_rejected`, process-lifetime, and the same recording is resent as WAV). The request timeout also scales with the audio (`request_timeout`: `cloud_stt_timeout_secs` + 0.5 s per second of audio, capped at 30 min), with a separate 10 s `CONNECT_TIMEOUT` reported as "Could not reach" so it gets the transient retry; the timeout is per request, not baked into the pooled client, so one pool serves every recording length. Two things did matter. First, `block_on_request` built a **fresh thread, runtime, and `reqwest::Client` per request**, which makes keep-alive impossible: a pooled connection belongs to the runtime whose I/O driver services it, so tearing that runtime down discarded the connection. There is now one process-lifetime multi-threaded runtime (one worker, which keeps polling the I/O driver between dictations so an idle connection survives the gap) plus a client cache keyed on base URL + key + timeout, with a 300 s idle timeout and TCP keep-alive; an interleaved 5-round A/B measured median 2.65 s fresh against 1.93 s pooled (~715 ms, 27%). Second — and larger — **the provider's route to the upstream model goes cold, and only a real transcription warms it**. A benchmark loop keeps that route hot; a person dictates once every few minutes and pays for it, which is why the app's log showed 3.5 s and 4.3 s for two real dictations while ten interleaved back-to-back rounds measured a p50 of 1.19 s. Across three runs with 4-minute idle gaps, no warm-up gave a 3.24 s median against 1.81 s after a single 0.25 s transcription first — ~1.4 s, ~44%, never worse. So `prewarm_cloud_stt` sends a **quarter-second tone through the ordinary transcription path** at recording start rather than the authenticated `GET /models` it used to send: that GET warmed DNS/TCP/TLS, none of which was the problem (the log confirms no new connection was opened before the `POST`). Cost is fractions of a cent per cold dictation, it is fire-and-forget, and `ROUTE_WARM_FOR` skips it when a real request finished within 30 s — biased heavily toward warming, because a redundant warm-up costs a quarter-second of audio and a skipped one costs the user two seconds. The warm-up is itself a cold request (~2.3 s), so it needs to fit inside the recording: at 4 s of speech one round gained 1.9 s and another only 0.4 s. One thing was measured and deliberately **not** done: hedging a duplicate request against the ~3 s tail (the spikes hit a bare client and the app's client in the _same_ round, so they are correlated provider-side stalls a duplicate does not escape). Compression was on that list too, for a fast uplink, and came off it when a slow one turned up (above). The residue beyond all this is round-trip distance; only a realtime WebSocket removes it by uploading during speech, which is why ElevenLabs `scribe_v2_realtime` feels immediate and OpenRouter, which has no realtime endpoint, cannot. Chunking a batch provider's audio during recording would buy live text but almost no latency, precisely because latency is flat in audio length. Latency on this path varies by a second run to run, so measure with repeats and medians — single samples have already produced three wrong conclusions here.

**Language is a source hint everywhere; translation only reaches English, and only on one schema.** `selected_language` is shared with the local engine and reaches every cloud provider as a recognition hint (`language_code` on ElevenLabs, `language` on the OpenAI schema and Deepgram) — the transcript still comes back in the language spoken. `cloud_language_code` strips script and region subtags on the way out, because the app's list carries `zh-Hans`/`zh-Hant` for the local variant conversion and no cloud endpoint here understands them; the Simplified/Traditional conversion still happens locally afterwards. **No cloud transcription API translates into an arbitrary target language** — not ElevenLabs, not OpenRouter, not Deepgram, not OpenAI — so "speak English, get Nepali" is not a thing any of them offer. English is the one exception and only on the OpenAI schema, whose separate `/audio/translations` route has its output language fixed to English; `CloudSttProvider::supports_translation` marks the providers that have it (OpenAI, Groq, and the custom entry, since self-hosted Whisper servers implement it) and `ResolvedCloudStt::translate` is the conjunction of that flag and the user's switch, so `transcribe_openai` can pick the route without re-deciding. A provider without the route logs a `warn!` naming itself and transcribes normally; the settings row says the same thing in place of a switch that would do nothing. On the local side the completion line only says `(translated)` when the engine was actually asked _and_ can do it (`ModelInfo::supports_translation`) — reading the setting alone made the log assert a translation that never happened, which is how a Japanese transcript came out of a run logged as "translated".

**Filler removal is one switch, not two.** `filter_transcription_output` (`audio_toolkit/text.rs`) used to run on every transcription with no off switch, so `cloud_stt_no_verbatim` only controlled the _provider-side_ flag — which several providers don't implement — and a user who turned it off still got their "um"s deleted. On the cloud path the setting now gates both layers: on asks the provider and runs the local filter as the backstop, off means verbatim. The local engines still filter unconditionally, as they always have. That filter also repairs the seams its own deletions leave (`repair_removal_seams`): removing a filler that opened a sentence used to produce `right? for example` — a lowercase sentence start — and two consecutive fillers left a doubled comma. Casing is repaired after `?` and `!` but never after `.`, because a full stop is also an abbreviation mark and `e.g. foo` must not become `e.g. Foo`; the first character of the transcript is left alone too, since dictation is frequently a mid-sentence continuation.

**A batch fallback changes the model, and the models disagree.** `scribe_v2` and `scribe_v2_realtime` are separate models with separate namespaces, and `batch_model_id` maps the realtime id onto its batch sibling so the fallback still works. Measured on one recording: batch gave "I guess it can do multiple languages… My Transcribe 2", realtime gave "I can just kind of do multiple languages… MyTranscribe2". So with streaming on, a socket hiccup produces materially different wording from the run before it — the substitution is logged at `info!` for exactly this reason. Turning "Transcribe as I speak" off pins every recording to `scribe_v2`, which is the lever to pull when comparing outputs.

- `assistant.rs` - Assistant turn pipeline (`run_assistant_turn`): LLM chat, screen vision, profiles/personas, per-profile response-length. Runs a bounded tool-calling loop (`llm_client::send_chat_stream_with_tools`, `tool_choice = "auto"`, max ~3 rounds) exposing `build_assistant_tool_capabilities()`. **The tool list is never empty**: `get_current_datetime` plus `set_reminder` / `list_reminders` / `cancel_reminder` go out on every turn, with `web_search` and `capture_screen` added only when their feature is on. The clock used to sit behind the web-search flag, which was wrong on its own terms and became a bug once reminders existed — "remind me at nine tomorrow" cannot be resolved without knowing what today is. Making the list unconditional needs one safety net, since a provider that rejects a `tools` array would now fail _every_ message rather than only web-search users': `is_tools_unsupported_error` plus a single no-tools retry (`tools_fallback`), guarded on nothing having streamed yet so a mid-reply failure can never restart a turn the user is reading. Injects the advisory personal-memory block late in the prompt and triggers offline memory distillation when a conversation ends. **Panel window lifecycle is main-thread-only:** `build_assistant_panel` / `present_assistant_panel` are private and every public entry point (`create_assistant_panel`, `show_assistant_panel`, `destroy_assistant_panel`) queues them via `run_on_main_thread`. Shortcut actions run on the keyboard engine's thread, and building a WebView window from there deadlocks the event loop — the whole app then freezes (no overlay, no dictation, undraggable windows). Queuing also keeps a create ordered behind a destroy, so a fast off → on of the master switch cannot leave the app believing in a window that is gone. **The quick ask is one fixed, transparent frame per show** (`ask_placement` / `ask_placement_on`): its size is the largest the answer card may grow to (display fraction by dock zone, clamped; the old size preset is gone — it only moved the ceiling of an invisible frame), it is placed at the dock zone on the display from `assistant_ask_display` (default `cursor`; the old `last_used` is migrated) on **every** show, and it never resizes or moves while an ask runs — the webview morphs a pill into the card inside it and `hitRegion.ts` passes the rest of the frame through. `assistant-ask-layout` tells the webview which edge of the frame is flush with the screen. This replaced a pill-sized window that faded out, waited, resized-and-moved, measured the card and faded back in, which is why answers could only appear once complete, and four stored positions (`LEGACY_POSITION_KEYS`, deleted on launch) that made the panel open somewhere different each time; only a live call remembers where it was dragged. **On Windows the quick ask does not take the foreground** (`ASK_KEYBOARD_ON_SHOW`): a voice ask harvests the selection with a synthetic Ctrl+C at the moment the hotkey goes down and Insert pastes back into the same field, so a panel that activated on show broke both; it is `WS_EX_NOACTIVATE` until the text field asks for the keyboard (`assistant-ask-keyboard` → `set_panel_keyboard`). Every quick ask starts from an empty conversation (`should_reset_quick_ask`) and hiding the panel clears it — there is no follow-up field; History's Continue opens the call instead (`continue_in_call`)
- `reminders.rs` - **Reminders**: "remind me to send that invoice in twenty minutes". A tool the model calls rather than a form the user fills in, so the whole interaction is one spoken sentence — and because the assistant can already see the screen, "look at this and remind me about it later" needs nothing extra. Three properties are what make it trustworthy rather than a toy. **A reminder outlives the app**: it is written to `reminders.json` on creation, and anything that came due while the app was closed fires on the next launch (`partition_due` treats "due a second ago" and "due yesterday" identically) — an alarm that only works if you never quit is one you stop checking. Something that fired and was never acknowledged is re-presented **once** at startup, not on every tick, because the popup's X exists so a reminder can be set aside without being marked done. **It arrives without stealing your work**: the popup is the recording overlay's discipline applied to a notification — always on top, `focused(false)`, and `focusable(false)` on Windows only (`WS_EX_NOACTIVATE`), since on macOS a non-activating window makes WebView buttons unreliable and Done/Snooze are the entire point. **It does not go away on its own**, and several due at once stack in one window rather than opening one each. Every scheduling decision is a pure function with the clock as a parameter (`resolve_due_at`, `next_wake`, `partition_due`), so the logic is unit-testable without sleeping; the scheduler is its own thread parked on a channel `recv_timeout` (woken by any change, capped at a 60 s poll so a laptop resume or a corrected system clock costs one interval rather than the whole delay) rather than a tokio task, which a long sleep would occupy. `resolve_due_at` reads a naive `at` as **local** time (what "at six" means) and refuses a past or sub-5-second time with a sentence the model can relay, because firing immediately interrupts the sentence the user is still speaking and silently moving it to tomorrow hides a wrong answer behind a right-looking one
- `memory.rs` - Local-first personal memory: a two-tier profile (always-on "About You" summary + durable notes) selected by keyword relevance within a per-turn token budget, learned via offline distillation at the end of a conversation, with safety guardrails (no secrets/PII, no instruction-shaped text, advisory-only) plus consolidation/decay/pruning
- `screenshot.rs` - Screen capture for vision: grabs the monitor under the mouse cursor (`capture_screen_data_url_at`, multi-monitor aware), adaptively JPEG-compresses to the provider's payload budget, and builds the small persisted display thumbnails (`data_url_to_thumbnail`)
- `llm_client.rs` - Shared OpenAI-compatible chat client used by the assistant, post-processing, and remote TTS: SSE streaming, tool-calling (the web-search path), structured/JSON-schema output, model listing, provider auth (Anthropic `x-api-key`, Azure `api-key`, OpenRouter `HTTP-Referer`/`X-Title`), Azure base-URL normalization to `/openai/v1`, and system-prompt folding for the built-in local engine (Gemma-style templates that reject a `system` role). Two invariants here exist because a **conversation can be silently bricked** otherwise. First, `enforce_alternating_roles` runs for **every** provider, not just the built-in engine: a strict chat template is a property of the model, not of who serves it, and Gemma on a cloud gateway rejects two consecutive `user` messages with HTTP 400 "Conversation roles must alternate" exactly like the local template does. Our own history produces that shape routinely — a voice barge-in cancels generation before the first token, so the user message is recorded with no assistant message after it — and because the offending pair stays in the conversation, _every_ later turn failed identically until the conversation was cleared. Dropping content-free assistant turns and merging adjacent same-role ones repairs the request at send time (a no-op on a well-formed conversation), so even a history already corrupted on disk works again. Second, an error the provider delivers **inside a 200 SSE stream** (`data: {"error":{…}}`, which is how Bedrock reports a rejected body) is parsed as `StreamErrorEnvelope` rather than skipped as a malformed frame: it used to be logged at debug and the round resolved to an empty answer, so the user got silence with no error anywhere. A mid-stream error that arrives _after_ tokens is logged and the partial reply kept, since dropping it would blank text already on screen

- `tts.rs` - Spoken answers (Kokoro local / OpenAI-compatible / ElevenLabs / Azure AI Speech). Only the `kokoro` engine synthesizes **inside the assistant WebView** (`src/assistant/useKokoroTts.ts` + `kokoro-js`): ~310 MB of fp32 ONNX weights, and on WebGPU a second copy as GPU buffers. Because the panel window is created at launch and only ever hidden, that used to be resident for the app's lifetime — and it loaded even for users on a remote engine. `src/assistant/localTts.ts` now holds the policy shared by the panel and Settings: load only when the selected engine is local (`localTtsActive`), prepare only while the panel is actually on screen, and release the session after an idle window (60 s hidden / 10 min visible) unless speech is in flight (`isSpeechInFlight`). Playback loudness is `assistant_tts_volume`, which is the assistant's **own** setting: it used to be `audio_feedback_volume`, whose only control is greyed out whenever the feedback beeps are off (the default), so turning the beeps down once and then switching them off left the voice quiet with nothing to turn it back up — and the old `.max(0.1)` floor existed for the same reason and is gone, so 0 now means silent. `voice_engine_blocker` is the precondition a hands-free call checks before it starts: a call speaks every reply regardless of `assistant_tts_enabled`, so it inherits a remote engine the user configured but never gave a key, which otherwise failed once per utterance forever with a generic provider error. Loopback OpenAI-compatible endpoints are exempt — a self-hosted speech server legitimately needs no key
- `audio_tags.rs` - **ElevenLabs audio tags** (`[laughs]`, `[whispers]`, `[applause]`), which Eleven v3/v4 act out or play as sound effects instead of reading. Three pieces live together so they cannot disagree: `active(settings)` is the single gate (engine is `elevenlabs`, the _requested_ model's `v<N>` segment is ≥ 3 via `model_supports_tags`, and `assistant_tts_elevenlabs_audio_tags` is on); `prompt_section(intensity)` is the system-prompt paragraph added only when the turn is spoken and the gate is open (fixed text per `AudioTagIntensity`, so the prefix stays cache-stable); and `strip` removes tags from text bound for every other engine. Stripping is needed even with the feature off, because tags written during an ElevenLabs call stay in the conversation history and a model imitates its own earlier replies after the user switches voice. The sanitizer therefore takes a `keep_audio_tags` flag (`sanitize_for_speech_for`, `sanitize_for_speech_chunk(_, keep)`, `SpeechChunker::keeping_audio_tags`), and `strip` is deliberately narrow — lowercase start, letters only, not glued to a word — so `[Ctrl]`, `[1]`, `[x]` and `items[idx]` survive. The panel shows the reply as written, tags included. `src/lib/ttsEngines.ts::elevenLabsModelSupportsAudioTags` mirrors the model rule for the settings switch, and Test voice plays tagged sample lines while the feature is active
- `native_tts.rs` - The **processor voice** (issue #29) and the **native-only voices**: Kokoro runs natively through sherpa-onnx for machines whose WebView cannot run it on the graphics card (no WebGPU, which is most Linux, or a driver that garbles it), and Kitten, Pocket TTS and Supertonic only ever run here. It is CPU-only on purpose: sherpa-onnx ships GPU builds only for NVIDIA CUDA (~0.5 GB, plus the CUDA and cuDNN runtimes), and these models are small enough that a batch-of-one GPU run gains little. Inside the WebView those machines got single-threaded WebAssembly, about 10 s per reply. Natively, all cores measured RTF 0.20 at 8 threads on a Ryzen 7700X, with the first sentence in about 0.3 s. **Nothing ships in the installer.** The engine (onnxruntime plus the sherpa C API, 7–12 MB per platform, pinned to 1.13.8 with a SHA-256 per platform) downloads with the first voice pack into `models/tts-runtime/sherpa-onnx-<ver>/` and is loaded with `libloading` at first use. It is deleted when the last pack goes, and `init` removes other versions at launch. The packs are ordinary catalog models (`EngineType::NativeTts`: `kokoro-82m-native` 350 MB, Kitten `kitten-nano-0.8` / `kitten-micro-0.8` / `kitten-mini-0.8` at 64 / 44 / 68 MB, `pocket-tts` 168 MB plus its voices, `supertonic-3-int8` 129 MB), so download, resume, cancel and delete are the model manager's own code. The native-only engines are `NATIVE_ENGINES` (`kitten`, `pocket`, `supertonic`); Kitten's size is that engine's `assistant_tts_model` (a catalog id, empty = nano, which is what every earlier version installed). **Pocket TTS has no built-in speakers**: each voice is cloned from a short reference recording, recording quality included, so its 14 voices are WAVs fetched after the archive (`install_voice_clips`) from `kyutai/tts-voices` pinned to one commit, each checked against a SHA-256 in `POCKET_VOICES`. Which recordings ship was decided by scoring every one (UTMOS naturalness plus speaker similarity): Kyutai's voice-donation clips (Marius, Javert) are phone recordings that rendered badly or ran away, and its default Alba is a 126 Hz recording that sounds mislabelled as a woman's voice, so those and the two lowest scorers are left out, as are the two non-commercial presets. Three Pocket settings are load-bearing, all measured. **fp32, not int8**: int8 scored lower and misread half again as many words (and k2-fsa/sherpa-onnx#3172 says the same by ear). **One call per sentence with a frame ceiling** (`pocket_pieces`, `pocket_max_frames`): Pocket's end-of-speech signal often never fires on short text, and the engine then generates to its 500-frame limit, 40 s of breathing for "Sure."; Kyutai's own fix (padding with spaces) does nothing through sherpa-onnx, which drops them. **Pauses kept whole** (`silence_scale` 1.0, not the 0.2 the other voices use). Temperature 0.3 and 1 flow step are Kyutai's defaults. Pocket is still weak on one- and two-word prompts even with the ceiling, and it follows its reference clip's pace, so it has no speed control. `is_downloaded` also requires the runtime to be present, and every file the pack's engine opens (`VoicePack::required_files`, which includes Pocket's clips). **One engine at a time**, dropped after `IDLE_UNLOAD` (180 s) or when the voice is switched away (Kokoro ~400 MB resident, Kitten ~80 MB). **Routing is Rust's call** (`route` → `VoiceRoute::{Webview, Native, Remote}`), but only a WebView can see the GPU, so the WebView reports it (`assistant_report_webgpu`) from three places: a cheap adapter probe (`useLocalVoiceStatus`), a WebGPU init failure, and the broken-audio check on the first two WebGPU clips (`audioLooksBroken` in `src/assistant/localVoice.ts`, calibrated on real speech: ZCR 0.05–0.14, RMS 0.06–0.13). A GPU that corrupts Kokoro throws nothing, so the samples are the only evidence. A failed check mutes the reply, persists `speakoflow.kokoro.gpuBroken` for Automatic, and moves the next reply to the processor. `assistant_tts_kokoro_device` is `auto` / `gpu` / `cpu`, and the old `q8-cpu` precision migrates to `cpu`. **Automatic never makes the voice worse**: it only goes native when WebGPU is unusable _and_ the pack is ready, otherwise Kokoro stays in the WebView. A library that refuses to load (macOS library validation on an ad-hoc-signed app is the expected case) latches `LOAD_FAILED` for the session, so every pack reads as not ready and Kokoro falls back rather than failing each reply. `local-voice-status-changed` tells the windows. Two FFI details matter. Windows loads with `LOAD_WITH_ALTERED_SEARCH_PATH`, because System32 ships an unrelated `onnxruntime.dll` (1.17) that a plain load binds to. Paths go through 8.3 short names, because the C API opens narrow strings in the ANSI code page. The `#[repr(C)]` structs mirror `c-api.h` 1.13.8 exactly, including model families the app never uses, since a missing field shifts every later one. Each model's own speed 1.0 is a different pace, so every pack carries a `pace` that maps the app's 1x to a normal speaking rate (Kitten nano 1.6, micro 1.5, mini 1.3, Supertonic 1.2, measured in words per minute against the same sentences). Kokoro is configured `lang=en-us` with no lexicon, which loads faster and uses 42 MB less; British voices pass `{"lang":"en"}`, because espeak rejects `en-gb`. The int8 variants were measured and rejected: ConvInteger makes Kokoro int8 slower than fp32 (RTF ~1.0). sherpa 1.13 statically includes eSpeak NG (GPL-3.0). It is downloaded at run time from upstream, never bundled or redistributed by us.
- `web_search.rs` - Optional web search, fully model-decided: the assistant calls a `web_search` tool and `run_tool_search` turns the tool args into a one-query `SearchPlan` fed to `search_with_plan` (parallel snippet search + local rerank) — there is no separate planner or keyword heuristic. Six snippet-only backends (Serper default, Brave, Tavily, Exa, SerpAPI, TinyFish); a `WEB_SEARCH_CAPABILITY_NOTE` is folded into the system prompt when search is enabled. OpenRouter's server-side `:online` search is the one opt-in exception for OpenRouter users
- `voice_conversation.rs` - Hands-free spoken sessions (the assistant panel's "call" mode). Session/turn tickets make late STT results and synthesized audio harmless after a barge-in, mute, or End. **A superseded utterance's transcript is carried forward, never dropped** (`carry` / `with_carried`): the frontend VAD ends an utterance after `TURN_PAUSE_MS` (450–1100 ms) of silence and starts a turn, so one thought spoken with a pause in it — "my name is Abhishek, <pause> can you help me with this?" — is two utterances, and resuming speech supersedes the first one's turn. Transcription almost always loses that race (the frontend interrupts ~160 ms into the resumed speech, while STT is still running, and on a cloud engine or a cold local model it is not close), so returning early on `!is_current` silently threw the first fragment away and the assistant answered only the words after the pause. Carried speech is scoped to the live session, expires after `CARRY_FORWARD_WINDOW` (so a fragment abandoned at mute does not reappear in front of the next question) and is capped at `MAX_CARRIED_CHARS`. A turn that starts and is _then_ cancelled needs none of this — its user message is already in history, and `llm_client::enforce_alternating_roles` merges the consecutive user messages at send time. `end_session` is also where a spoken conversation reaches memory: closing the panel during a call defers distillation (`assistant::distill_conversation_if_ended`) to the hang-up, because a live call is not an ended conversation. **Closing the panel hangs up, and hanging up closes the panel.** Hiding used to leave the microphone open, every utterance still answered and spoken aloud from a window that was no longer visible, while the X read as "hang up". `hide_assistant_panel` therefore ends the session (so the hotkey and tray paths agree with the button). The other direction was the mirror-image bug: ending the session left the window up, so the panel re-rendered as the quick-ask card and End looked like it had opened a second, different assistant. So **every** hang-up goes through `hide_assistant_panel` rather than `voice_conversation::end`: the End button and the in-webview Escape (`onHangUp`, threaded into `useVoiceConversation` because the hook cannot reach the window), the `assistant_call` shortcut's second press, and the global Esc. Esc is the one conditional case — mid-reply it stops the reply and keeps the call, and only hangs up when the assistant is idle, because hanging up mid-answer discards the thing the user is listening to. `voice_conversation::end` on its own is still what the _assistant_ shortcut calls, which must take the microphone back and then show the quick-ask card. **Dictation does not hang up a call; it holds it.** It used to, because both want the microphone, and the hang-up threw the call's whole conversation away to type one sentence somewhere else. Now `DictationTracker` (`dictation_started` in `TranscribeAction::start`, before the mic opens; `dictation_recorded` the moment `stop_recording` returns; `DictationFlight` ending the pipeline on every exit path; `dictation_cancelled` on a cancelled or failed start) emits `assistant-conversation-dictation` and the call's VAD pauses until recording ends, exactly as the mute button pauses it — a reply already on its way keeps playing, and the two switches are independent (`syncMic` in `useVoiceConversation` serializes both onto the VAD, so ending a dictation never unmutes a muted call). The tracker has three stages because the microphone and Esc are released at different times: the call listens again as soon as the audio is in, but Esc belongs to the dictation until it has pasted (`esc_hangs_up`), and a cancel during a dictation leaves the call's reply, voice and state alone (`cancel_spares_call` in `utils::cancel_current_operation`). Generations stop a pipeline released early by the coordinator's processing cap from ending a newer dictation's hold. A call started mid-dictation begins held (`call_may_start`; the webview asks `assistant_conversation_dictation_active`, since it missed the event), and while a call is up the bottom-docked recording overlay rises to `assistant::CALL_STACK_CLEARANCE` so it never covers the call bar. And because Rust considers a call active from the moment it issues the ticket — before that id reaches the webview — `assistant-conversation-ended` is honoured by a frontend session that has no id yet (`closedSessions` distinguishes that from a previous session's late event); requiring the ids to match left the VAD holding the microphone for a call the backend had already torn down. The pause the VAD waits for is fixed at `TURN_PAUSE_MS.natural` (700 ms): the panel passes `pace: null`. The "time to finish speaking" dial that used to set it (`assistant_conversation_pace`, still persisted and still accepted by `useVoiceConversation`) was removed from the call's options because it asked people to tune a number they cannot reason about, and a stored value must not keep applying with no control left to change it
- `transcription_coordinator.rs` - Single-threaded recording state machine; also owns `recording_mode`, which maps the `push_to_talk` setting onto `Hold` or `Lock`, and `Abort`, which throws away a recording whose press the hotkey engine withdrew. `claim_processing` lends its idle stage to a dictation being recovered, so a hotkey pressed during an Undo is "busy" instead of a second dictation racing it for the overlay and the paste
- `dictation_recovery.rs` - **Undo for a dismissed or failed dictation.** Cancelling used to be final: Esc mid-recording threw the audio away (`AudioRecordingManager::cancel_recording` discarded it), and a cancel or a failure later in the pipeline dropped whatever was already done. Now each leaves an `Offer` — what is left to do (`Remaining::Transcribe` / `Deliver` / `Paste`) plus its History row — and the pill turns into a quiet "Dismissed · Undo" or "Transcription failed · Try again" for 2.5 seconds (`overlay::show_recovery_overlay`, held open by hover). The offer is keyed by the overlay epoch that showed it, so a click on a pill that has since been replaced can never act on another dictation, and it is withdrawn the moment anything else takes the overlay. Taking it (`recover_dictation` → `actions::start_recovery`) resumes the dictation where it stopped, through the **same** `deliver_transcription` the live pipeline uses, so a recovered dictation pastes exactly what the original would have. Every dismissed dictation also keeps a History row with `dismissed = 1`, which counts nothing toward usage until it is recovered (`counted_words`), and History's Recover (`recover_history_entry`) finishes it without pasting. Three things are deliberately **not** offered: under half a second of speech (`worth_keeping` — a stray hotkey press cancelled on purpose), anything headed for the assistant or an in-app field (recovering pastes, the wrong destination for both), and any platform where a clickable overlay could take keyboard focus from the paste target (`live_card_takes_pointer`, so X11 without layer shell keeps the old hide)
- `autolearn/` - **"Learn words I correct"** (Windows only; macOS/Linux report `supported: false` and the UI says so). After a successful paste, `watch.rs` reads the one focused control over UI Automation for a minute and `detect.rs` turns a one-word fix into a `learned_words` entry, which `recognition_words` feeds to every engine. The first version learned nothing for anyone: it read the field once, milliseconds after a synthetic Ctrl+V the target had not processed yet, and it trusted `ValuePattern`, which on a Chromium web document is the page **URL**. So every dictation logged "the focused control does not contain the transcript". The watcher now retries acquisition for `ACQUIRE_FOR` (4 s), reads both Value and Text patterns and watches whichever actually holds the transcript, and only judges a reading once it is unchanged across two polls (`Settle`), so a word caught half-typed is never learned. When acquisition fails, the log names the control type, class, framework and pattern lengths, never the text
- `actions.rs` - Post-recording output pipeline: pastes the transcript and runs the optional, experimental **AI Correction** post-processing pass (`post_process_transcription`, `resolve_post_process_provider_and_model`, `prewarm_builtin_llm`) — cleanup plus a tone directive (`PostProcessTone::directive()`) in a single LLM call, wrapped in `tokio::time::timeout(post_process_timeout_secs)` and falling back to the raw transcription on timeout or failure. Cleanup runs on its **own** llama.cpp process (`CleanupLlm`, port 11436) which `prewarm_builtin_llm` starts _and warms with a real prefill_ at recording start; `prewarm_assistant_llm` does the same for the assistant's engine. Output is validated by `validate_cleaned_output` → `sanitize_post_process_output` (strips fences, `<transcript>` tags, leaked `<think>` blocks) plus `is_implausibly_long`, which rejects the classic small-model failure of narrating a plan instead of cleaning the text
- `overlay.rs` - Recording overlay window (platform-specific). Two properties matter more than the drawing. **It must never take keyboard focus.** The window is deliberately larger than the visible pill (the pill hugs its content and floats inside a transparent frame), so most of it was invisible padding that sat in front of the user's app, swallowed clicks, and — because a click _activated_ it — moved keyboard focus off the field being dictated into, after which the synthetic Ctrl+V pasted the transcript into the overlay's own webview and it vanished. The compact pill never takes the pointer. The live card takes it from the first word wherever the window cannot take keyboard focus, which `live_card_takes_pointer` decides per platform: Windows sets `WS_EX_NOACTIVATE`, macOS uses a panel that never becomes key, and a GTK layer surface is created with `KeyboardMode::None`. Scrolling back through live text, selecting a phrase, and the copy button are why the card exists, and a click-through card drew all three while letting none of them work. `ShowOverlayPayload.interactive` tells the webview which case it is in, so it never offers a control the window would pass straight to the app underneath. A click can focus an ordinary X11 window, so there the card stays click-through until `finish_recording_overlay` hands the pointer back after the paste. On Windows it is also `set_focusable(false)` (`WS_EX_NOACTIVATE`) so a click that does land cannot take the foreground at all. **And it must stay on top for a whole recording, not just the moment it appears.** `force_overlay_topmost` ran once per show, but `WS_EX_TOPMOST` is a position another process can take; `start_overlay_topmost_guard` re-asserts it on a 700 ms tick while the overlay is up and `warn!`s once per displacement naming whether topmost or visibility was lost — which is what turns "the dictation window hides randomly" into a log line. The guard's generation counter is retired by `hide_recording_overlay` _before_ the window goes down, so a tick already queued on the main thread cannot resurrect a deliberately hidden overlay. `get_monitor_with_cursor` hit-tests the cursor against monitor bounds in physical pixels first and logical points second, rather than pre-scaling the bounds: the cursor is physical on Windows/X11 and logical on macOS, and scaling only one side made every monitor look smaller than it is, so on a scaled multi-monitor desktop the overlay fell back to the primary display
- `audio_feedback.rs` - Feedback-sound playback with selectable themes (`SoundTheme`: Default/Marimba/Pop/Click/Custom, resolved per start/stop from bundled resources), `play_test_sound` for in-settings previews, and `play_reminder_sound` — the one cue **not** gated on `audio_feedback`, because that switch means "don't beep when I start dictating" and a reminder whose whole job is to reach someone looking elsewhere must not be silenced by it. - `signal_handle.rs` - `send_transcription_input()` reusable function
- `speech_readiness.rs` - The gate every voice shortcut passes before it records (`TranscribeAction` / `AssistantAction` / `AssistantCallAction`). First-run setup starts the speech model downloading and then tours the app, so the first press often comes before the model has landed; the press used to open a recording that could only fail. `resolve` is a pure function over a snapshot (cloud configured, the selection, the catalog): a downloaded selection or a complete cloud setup is ready; a speech model downloading refuses the press and shows the overlay's `downloading` pill (`overlay::show_speech_download_overlay`), which follows that model's `model-download-progress`; nothing on disk and nothing coming shows the `noSpeechModel` notice. A download in flight wins over a stale model on disk, because the setup queue selects a model only once its file lands. Hanging up a call is never refused
- `updates.rs` - What the updater plugin does not decide: whether **this** install can replace itself (`resolve_install_mode` → `UpdateInstallMode`: `InApp` / `Download` / `Portable` / `PackageManager`), and the manual fallback (`download_update_installer`, which saves the right full installer to Downloads from the `speakoflow.downloads` block of `latest.json`, and `open_update_installer`). The plugin would happily do the wrong thing on Linux: an install with no bundle type (from source, AUR) falls through to its AppImage path and overwrites the running binary, and a `.deb` is installed with `dpkg -i` even on Arch. So in-place install is offered only for NSIS/MSI, macOS, a running AppImage (`APPIMAGE` set), and a `.deb` on a Debian-family system with a way to ask for the password. Downloads are confined to this repo's `releases/download/` URLs and plain `SpeakoFlow*` file names. **A Windows in-app install skips `RunEvent::Exit`**: the plugin starts the installer and calls `std::process::exit` itself, so `prepare_update_install` (which the frontend calls between `download()` and `install()`) runs `lib.rs::release_before_exit` first on Windows, the same meeting stop and engine teardown every ordinary quit gets. macOS and Linux need nothing extra, because their relaunch goes through `request_restart`, which does fire `RunEvent::Exit`
- `feedback.rs` - In-app feedback. `send_feedback` posts to the Cloudflare Worker in `feedback-worker/` (`FEEDBACK_ENDPOINT`), which files an issue in the private `AbhishekBarali/speakoflow-feedback` repo. Sent from Rust, not the webview, so there is no CORS surface; the Worker answers no preflight. What is sent is exactly what the dialog shows: message, email only if typed, up to three screenshots (pasted or picked, shrunk in `components/feedback/screenshots.ts` to ≤1920 px WebP/JPEG around 100–400 KB, committed by the Worker under `attachments/YYYY-MM/` and embedded in the issue), and the system line only if its box is ticked. No logs, no transcripts. The Worker's credential needs Contents: write as well as Issues for screenshots; without it the report still arrives and the issue says its images were not stored
- `utils.rs` - Platform detection helpers

The fill is budgeted from this machine's own history (a decaying fit of stage time on recording length, in `localStorage`), eases out gently within the estimate and creeps on a hyperbolic tail past it, and is capped at 94%, so only the real finish runs it out. **Its speed never jumps**: the drawn fill rides the curve through a critically damped spring on its offset _and relative speed_ (so a steady curve is followed with no lag; damping absolute speed trailed it by ~0.17s, over half a quick local dictation) and the finish is a Hermite run-out that starts at the current speed and lands at rest, as short as an acceleration cap allows (`sealDuration`, 120–280 ms) — the first version computed position straight from the curve and measured ×2.5 in speed at the cleanup hand-off and ×13 at the finish, which read as jerky and made a fast dictation feel slow (`workProgress.test.ts` bounds the per-frame change). **It ends with the text**: `paste_final` sends `seal-overlay` (`overlay::seal_working_overlay`) when the text is ready, before the paste, because the words appear at the keystroke and the paste's own tail (100 ms modifier hold, 50 ms clipboard restore) used to delay the run-out until the fill finished ~0.4 s after them; the compact pill's hold (`PILL_SEAL_HOLD_MS`) counts from that seal. The estimate's floor applies to the prediction, not the fit's intercept, which had lifted every estimate for a machine faster than the prior (0.51 s for waits of 0.30 s). **There is no completion mark**: a full, still row is the ending, because the pasted text is the real confirmation, and a tick drawn after every dictation read as slow and childish. The waveform freezes on that row while the window fades (`freeze`) instead of dropping to rest. `cleanupNext` on the transcribing show reserves cleanup's share so the bar does not fill and then start over. The compact pill holds `PILL_SEAL_HOLD_MS` after success so the run-out is seen. Flow's `generating` / `vision` keep the looping ripple, since nothing estimates them.
- `lib/types.ts` - Shared TypeScript type definitions

### Key Architecture Patterns

**Self-update does not need code signing.** The updater verifies a minisign signature made with our own free key (public half in `tauri.conf.json`, private half in the `TAURI_SIGNING_PRIVATE_KEY` / `_PASSWORD` repo secrets, key id `73D1FDFF87780381`). Apple/Azure code signing is a separate, paid thing that only affects first-install warnings. Until 2.0.0 the two were tied together in CI, and the app also trusted upstream Handy's key, so no release from 1.0 to 1.4 ever had a working update path — and the only update UI was rendered with `className="hidden"`. Now: `build.yml` keeps `createUpdaterArtifacts` whenever the key secret exists (`HAS_UPDATER_KEY`), re-signs the Linux AppImage and `.deb` **after** they are repacked (the bundler's signatures describe pre-repack bytes), and `updater-manifest.yml` writes `latest.json` once, at the end, from the `.sig` files actually on the release, verifying every signature against the published bytes (`scripts/ci/updater-manifest.ts`, tested with a real signature). tauri-action's own `latest.json` is off (`includeUpdaterJson: false`). Installed apps poll `releases/latest/download/latest.json`, which GitHub serves only from the newest published non-prerelease release, so a draft or a beta never reaches anyone. On the frontend, `update-checker/updateStore.ts` is the one state machine; `UpdateChecker` runs the checks (8 s after launch, then every 12 h; `update_checks_enabled` only disables the automatic ones), `UpdatePill` announces a found update at the bottom of the sidebar, and `UpdatePanel` in Settings → About shows notes and the install / download action for the install mode. **Losing the private key means installed apps can never update again** — it lives at `~/.tauri/speakoflow-updater.key` on the maintainer's machine and in the repo secrets; back it up.

**Feedback** is the "?" beside Settings in the sidebar, "Send feedback…" in the tray, and a row in Settings → About (`components/feedback/`). The draft is saved as it is typed, so closing the dialog or a failed send loses nothing. The Worker (`feedback-worker/`, deploy steps at the top of its `wrangler.toml`) validates with the same limits as the app, rate-limits per address and globally, defuses `@mentions`, and authenticates to GitHub as a GitHub App (issues opened by a bot, so the owner is emailed) or with a fine-grained PAT (issues opened as the owner, who is not emailed about their own activity by default).

**Manager Pattern:** Core functionality organized into managers (Audio, Model, Transcription) initialized at startup and managed via Tauri state.

**Command-Event Architecture:** Frontend → Backend via Tauri commands; Backend → Frontend via events.

**Pipeline Processing:** Audio → VAD → Whisper/Parakeet → Text output → Clipboard/Paste

**State Flow:** Zustand → Tauri Command → Rust State → Persistence (tauri-plugin-store)

**Custom Title Bar:** Native window decorations are disabled on Windows/Linux (`decorations(false)` in `lib.rs`); the webview draws the chrome via `TitleBar.tsx` (brand + minimize/close, which needs the `core:window:allow-minimize`/`allow-close` capabilities). macOS keeps the window decorated with an overlay title bar (`TitleBarStyle::Overlay` + `hidden_title`) so the native traffic lights still work. Close hides to the tray (see `on_window_event`).

**Paste Safety Net:** Synthetic-paste flows (`input.rs`) always release modifiers after a key combo, via `input::release_all_modifiers`, so an interrupted paste can never leave Ctrl/Shift/Alt/Cmd stuck "pressed" at the OS level.

**Synthetic input must not be read back as a hotkey.** Every synthetic key sequence in `input.rs` and `clipboard.rs` opens `input::synthesizing()`, which raises a counter the vendored handy-keys Windows hook consults (`vendor/handy-keys/src/injected.rs`); an `LLKHF_INJECTED` event arriving while it is up is passed through to the target app but withheld from hotkey matching. Without it the assistant's hold-to-talk recorded nothing: `AssistantAction::start` harvests the focused app's selection with a synthetic Ctrl+C, and the injected Ctrl key-up matched the modifier-only `Ctrl+Alt` binding as a release, ending the recording ~30 ms after it began. `input::conflicting_modifier_held` was written to prevent exactly that and could not, because it asks `GetAsyncKeyState` whether Alt is down and the hook had _blocked_ that Alt key-down from ever reaching Windows — the blind spot is now documented on the function. The guard is a window rather than a blanket `LLKHF_INJECTED` filter so a macro keyboard or accessibility tool that fires a registered hotkey still works. `send_copy_combo` additionally borrows a Ctrl the user is already holding instead of pressing and releasing its own, which would desync the OS from the key still under their finger.

**Dictating into our own main window is an event, not a paste.** `paste_final` holds the main thread from writing the clipboard through restoring it, and a webview's Ctrl+V is only handled once that thread is free, by which time the clipboard is back to the user's content, so a paste into any field of the main window (onboarding's try-it box, a search field) silently did nothing while every other app worked. When the main window is focused and the recording did not start in another app (`delivers_in_app`), the final text is sent as `dictation-into-focus` and `src/lib/insertDictation.ts` inserts it at the caret with `execCommand("insertText")`, which React's controlled fields and the undo stack both see.

**Paste target:** a synthetic Ctrl+V reaches whatever holds keyboard focus at the instant it is sent, and the gap between the shortcut and the paste is a whole recording plus a transcription plus an optional LLM pass. `input::remember_paste_target` records the foreground window at recording start (`TranscribeAction::start`) and `restore_paste_target` hands it back from `clipboard::paste_with_behavior` — but **only when one of our own windows took the foreground**, which is the unambiguous failure and also the only case Windows lets us repair, since `SetForegroundWindow` is granted to the process that already owns the foreground. A switch to a _different application_ is logged and respected: someone who alt-tabs mid-dictation usually means to dictate into the window they switched to, and stealing focus back would be a worse bug than the one being fixed. A foreground window that is ours at recording start records no target, so the in-app dictation paths are untouched. Windows-only by construction: the overlay is a non-key NSPanel on macOS and a `KeyboardMode::None` layer surface on Wayland, so neither can take focus in the first place.

**Personal Memory (local-first):** `memory.rs` maintains a two-tier profile — an always-on "About You" summary plus durable notes selected by keyword relevance within a per-turn character/token budget (the `MemoryDetail` dial: Light/Balanced/Detailed). `build_memory_block` appends an advisory, delimiter-wrapped block late in the prompt in `run_assistant_turn` (kept late so the earlier prefix stays cache-friendly). Learning ("distillation") runs OFF the hot path at the end of a conversation — when the panel is hidden (`hide_assistant_panel`), the conversation is cleared (`assistant_clear_conversation`), or the user clicks "Update memory" (`assistant_distill_memory_now`) — reusing the active assistant provider (which can be the fully-offline built-in engine). A `last_distilled_len` dirty-guard prevents redundant passes. Safety is layered: capture, consolidation, and injection all reject secrets/PII and instruction-shaped text (`is_sensitive`), injected memory never overrides the user's current message, and consolidation dedupes/merges (Jaccard overlap), decays stale low-confidence auto notes (~45 days), and prunes to a hard cap. Off by default; an Incognito toggle skips both use and learning for a conversation. It's all stored on-device in settings and fully user-editable/exportable in Settings → Memory.

**Screen Vision (two switches, the model decides):** screen access is two settings, one per surface — `assistant_ask_screen_access` (the quick ask) and `assistant_call_screen_access` (a call), both **off by default** because a screenshot goes to whichever provider the user chose. On does not mean "capture": it means the turn is offered the `capture_screen` tool (`screen_access_for_turn`, never for the Cat persona) and the model decides per message. What it decides with is `screen_tool_guidance`, and the wording is the feature: look when the user asks ("look at my screen") or when the message is about something visible it was not given as text ("this error", "reply to this email"); never for anything answerable blind (general knowledge, writing, the time, reminders); and text inside `<selected_text>` **is** the "this" — answer from it and do not look unless explicitly asked. The previous guidance keyed on phrases like "what does this mean" and said nothing about selections, so "select three words, ask what this is" matched it exactly and screenshotted the desktop. The tool is deliberately _not_ withheld when a selection is present, because that also made "look at my screen" impossible with text selected. There used to be a third mode, **Manual** (a camera toggle and a region snip in the typed bar, with its own authorization tokens, an armed flag, a snip overlay window and a pending-attachments mirror); it and all of that machinery are gone, and `normalize_settings_json` migrates stores conservatively — only `agent_decides` turns the switches on; Manual (the old default) and Off turn them off, since the alternative would start sending screenshots nobody agreed to send. `screenshot.rs` captures the monitor under the mouse cursor (`capture_screen_data_url_at`) and adaptively JPEG-compresses to the provider's payload budget (verified against Azure's tight cap). `VisionCaptureTiming` only changes _when_ the frame is taken, never whether it is sent: `Immediate` (default) parks one at recording start in `AssistantAction::start` (`begin_agent_capture`, quick ask only), `OnSend` starts it at the top of the turn (`ensure_agent_capture_started`), and a frame the model never asks for is dropped at the end of the turn (`clear_agent_capture`) without leaving the device. A call never pre-captures — every utterance is a turn, so that grabbed the screen continuously — and `agent_capture_screen` captures on demand instead, re-checking the asking surface's switch at dispatch. Every screenshot the model takes adds the screenshot marker and a persisted display thumbnail (`ChatMessage.images`) to the user message, shown inline in the panel and history with click-to-enlarge; only that thumbnail persists, and the full-resolution frame is sent once.

### Application Flow

1. **Initialization:** App starts minimized to tray, loads settings, initializes managers
2. **Model Setup:** First-run downloads preferred Whisper model (Small/Medium/Turbo/Large)
3. **Recording:** Global shortcut triggers audio recording with VAD filtering
4. **Processing:** Audio sent to Whisper model for transcription
5. **Output:** Text pasted to active application via system clipboard

### Settings System

Settings are stored using Tauri's store plugin with reactive updates:

- Keyboard shortcuts (configurable, supports push-to-talk)
- Audio devices (microphone/output selection)
- Model preferences (Small/Medium/Turbo/Large Whisper variants)
- Audio feedback and translation options

### Single Instance Architecture

The app enforces single instance behavior — launching when already running brings the settings window to front rather than creating a new process. Remote control flags (`--toggle-transcription`, etc.) work by launching a second instance that sends args to the running instance via `tauri_plugin_single_instance`, then exits.

## CLI Parameters

SpeakoFlow supports command-line parameters on all platforms for integration with scripts, window managers, and autostart configurations.

**Implementation:** `cli.rs` (definitions), `main.rs` (parsing), `lib.rs` (applying), `signal_handle.rs` (shared logic)

| Flag                     | Description                                                |
| ------------------------ | ---------------------------------------------------------- |
| `--toggle-transcription` | Toggle recording on/off on a running instance              |
| `--toggle-post-process`  | Toggle recording with post-processing on/off               |
| `--toggle-assistant`     | Toggle an ask to the assistant on/off                      |
| `--toggle-call`          | Start a conversation with the assistant, or end it         |
| `--cancel`               | Cancel the current operation on a running instance         |
| `--start-hidden`         | Launch without showing the main window (tray icon visible) |
| `--no-tray`              | Launch without system tray (closing window quits the app)  |
| `--debug`                | Enable debug mode with verbose (Trace) logging             |

**Key design decisions:**

- CLI flags are runtime-only overrides — they do NOT modify persisted settings
- Remote control flags work via `tauri_plugin_single_instance`: second instance sends args, then exits
- `send_transcription_input()` in `signal_handle.rs` is shared between signal handlers and CLI
